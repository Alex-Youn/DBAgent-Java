## 무엇을 검증하는가 (15개 체크, 실행 시 전부 `[OK]`)

1. 최초 기동 시 키 파일 자동 생성 (운영자 조작 없음)
2. 암호화→복호화 왕복이 원본과 일치
3. 같은 평문도 암호화마다 다른 암호문(IV 랜덤 — GCM 안전성의 핵심 전제)
4. 변조된 암호문은 예외로 실패(GCM 인증 태그 검증)
5. 레거시 `B64(...)`/평문 값이 그대로 통과(마이그레이션 혼재 상태 대응)
6. `needsReencrypt()`가 평문/B64/구키를 정확히 재암호화 대상으로 골라냄
7. **다른 서버로 `dbconfig.db`만 복사해온 경우** — 복호화가 명확히 실패하는지(환경별 독립 키 결정의 실제 동작 확인)
8. 키 로테이션(k1→k2, 구키 보존) 후에도 구 암호문 복호화 + 재암호화 정상 동작

## 이 프로토타입을 돌리면서 설계문서보다 더 정확해진 부분

- **6번 시나리오의 실패 원인**: 설계 당시엔 "keyId를 못 찾아서"(`IllegalArgumentException`) 실패할 거라 예상했지만, 실제로는 두 서버 모두 키를 자동 생성할 때 기본 keyId를 똑같이 `k1`로 쓰기 때문에, 실무에서는 "keyId는 있는데 값이 달라 인증 태그가 안 맞음"(`AEADBadTagException`, `RuntimeException`으로 래핑)으로 떨어지는 경우가 더 흔합니다. **결과(복호화 실패)는 설계 의도와 동일**하지만, 로그에 찍히는 예외 메시지가 다를 수 있다는 점은 실제 구현 시 로그 문구를 다시 확인할 필요가 있습니다.

## 파일 구성

- `MasterKeyProvider.java` — 키 파일 로드/자동생성/`Cipher.getMaxAllowedKeyLength("AES")` 기반 128/256비트 자동 폴백
- `CredentialCipher.java` — `ENC(v1:keyId:base64(IV+CT+TAG))` 포맷 암복호화, 레거시 통과, `needsReencrypt()`
- `Demo.java` — 위 시나리오 8가지를 순서대로 실행하고 pass/fail 집계
- `run.ps1` — 컴파일+실행 스크립트
- `.gitignore` — 실행 중 생성되는 `*.key`(실제 AES 키가 든 데모 산출물)와 `*.class`를 git에서 제외
