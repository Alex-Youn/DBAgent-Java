# DB 세션 조회 및 모니터링 쿼리 정리

> 원본: `세션리스트 및 세션 정보 조회 쿼리.txt` (CP949 인코딩)
> 용도: RDB 모니터링 대시보드(PostgreSQL / MySQL / MariaDB / MS SQL Server) 구현용 쿼리 모음
> 정리일: 2026-09-04 · 이 문서는 UTF-8

---

## 1. 화면 구성별 쿼리 3종

각 DBMS마다 아래 세 가지 쿼리가 한 세트로 필요합니다.

| # | 화면 | 목적 | 쿼리 특징 |
|---|---|---|---|
| 1 | **세션 리스트** | 활성 세션 목록 그리드 | SQL을 `LEFT(..., 500)`으로 잘라 미리보기만 |
| 2 | **세션 상세 팝업** | 특정 세션 클릭 시 | SQL **전문**(`sql_text`) 조회 |
| 3 | **Lock 블로킹 체인** | 대기(waiter) ↔ 유발(blocker) 관계 | 두 세션을 조인해 쌍으로 표시 |

공통 필터 원칙:

- **모니터링 쿼리 자신을 제외** — PostgreSQL `pg_backend_pid()`, MySQL/MariaDB `CONNECTION_ID()`, MS SQL `@@SPID`
- **유휴 세션 제외** — PostgreSQL `state != 'idle'`, MySQL/MariaDB `command != 'Sleep'`, MS SQL `is_user_process = 1`

---

## 2. DBMS별 개념 매핑

Oracle 기준 개념이 각 DBMS에서 무엇에 대응하는지 정리한 표입니다.

| 개념 | Oracle | PostgreSQL | MySQL / MariaDB | MS SQL Server |
|---|---|---|---|---|
| 세션 식별자 | SID | `pid` | `id` | `session_id` (SPID) |
| 조회 대상 | `v$session` | `pg_stat_activity` | `performance_schema.processlist` (MySQL)<br>`information_schema.PROCESSLIST` (MariaDB) | `sys.dm_exec_sessions` + `sys.dm_exec_requests` |
| SQL 전문 | `v$sql` 조인 | `query` (**조인 불필요**) | `info` (**조인 불필요**) | `sys.dm_exec_sql_text()` (OUTER APPLY) |
| 계정 | `username` | `usename` | `user` | `login_name` |
| 접속 IP | `machine` | `client_addr` | `host` | `host_name` |
| 프로그램명 | `program` | `application_name` | — | `program_name` |
| 경과 시간 | — | `clock_timestamp() - query_start` | `time` (초) | `total_elapsed_time` (**ms**) |
| 대기 이벤트 | `event` | `wait_event_type`, `wait_event` | `state` | `wait_type` |

> **핵심 차이:** PostgreSQL과 MySQL/MariaDB는 세션 정보와 실행 중인 SQL이 **한 뷰에 함께** 있어 조인이 필요 없습니다. MS SQL Server만 세션 뷰·요청 뷰·SQL 텍스트 함수 3개를 조인해야 합니다.

## 3. PostgreSQL

### 3.1 세션 리스트

```sql
SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    wait_event_type,
    wait_event,
    ROUND(EXTRACT(EPOCH FROM (clock_timestamp() - query_start))::numeric, 2) AS duration_seconds,
    LEFT(query, 500) AS query_preview
FROM pg_stat_activity
WHERE state IS NOT NULL
  AND state != 'idle'               -- idle 세션 제외 (트랜잭션 미종료 idle은 포함)
  AND pid != pg_backend_pid()       -- 모니터링 쿼리 자체 제외
ORDER BY query_start ASC NULLS LAST;
```

### 3.2 세션 상세 (SQL 전문)

`pg_stat_activity` 뷰 하나에 세션 접속 정보와 SQL 전문(`query`)이 모두 포함되어 조인이 필요 없습니다.

```sql
SELECT
    pid,                                    -- 세션 식별자 (Oracle의 SID)
    usename,                                -- 계정
    client_addr,                            -- 접속 IP
    application_name,                       -- 프로그램명
    state,                                  -- 상태 (active, idle 등)
    ROUND(EXTRACT(EPOCH FROM (clock_timestamp() - query_start))::numeric, 2) AS elapsed_sec,
    wait_event_type,                        -- 대기 이벤트 타입
    wait_event,                             -- 대기 이벤트
    query AS sql_text                       -- 현재 실행 중인 전체 SQL
FROM pg_stat_activity
WHERE state != 'idle'                       -- 대기 세션 제외
  AND pid != pg_backend_pid();              -- 내 쿼리 제외
```

### 3.3 Lock 모니터링 (블로킹 체인)

```sql
SELECT
    blocked.pid                        AS waiter_pid,
    blocked.usename                    AS waiter_user,
    blocked.client_addr                AS waiter_ip,
    ROUND(EXTRACT(EPOCH FROM (clock_timestamp() - blocked.state_change))::numeric, 2) AS wait_duration_sec,
    blocked.wait_event_type,
    blocked.wait_event,
    LEFT(blocked.query, 300)           AS waiter_query,
    blocker.pid                        AS blocker_pid,
    blocker.usename                    AS blocker_user,
    blocker.state                      AS blocker_state,
    LEFT(blocker.query, 300)           AS blocker_query
FROM pg_stat_activity blocked
JOIN LATERAL UNNEST(pg_blocking_pids(blocked.pid)) AS blocker_pid(pid) ON true
JOIN pg_stat_activity blocker ON blocker.pid = blocker_pid.pid
ORDER BY wait_duration_sec DESC;
```

> `pg_blocking_pids()`가 블로커 PID 배열을 돌려주므로 `UNNEST`로 펼쳐 1:N 블로킹 관계를 그대로 표현합니다.

## 4. MySQL / MariaDB

> ⚠️ **MySQL과 MariaDB는 세션 조회 뷰가 다릅니다. 같은 쿼리를 공용으로 쓸 수 없습니다.**
> MariaDB에는 `performance_schema.processlist`가 **존재하지 않습니다**. 아래 4.1과 4.2로 분기해야 합니다.

### 4.1 세션 리스트 — MySQL 8.0+

```sql
SELECT
    id AS session_id,
    user,
    host,
    db,
    command,
    time AS duration_seconds,
    state,
    LEFT(info, 500) AS query_preview
FROM performance_schema.processlist
WHERE command != 'Sleep'          -- 대기 중(Sleep)인 세션 제외
  AND id != CONNECTION_ID()       -- 모니터링 세션 제외
ORDER BY time DESC;
```

### 4.2 세션 리스트 — MariaDB

원문에는 없던 대체 쿼리입니다. `FROM` 절만 `information_schema.PROCESSLIST`로 바꾸면 나머지는 동일합니다.

```sql
SELECT
    id AS session_id,
    user,
    host,
    db,
    command,
    time AS duration_seconds,
    state,
    LEFT(info, 500) AS query_preview
FROM information_schema.PROCESSLIST   -- MariaDB는 performance_schema.processlist 없음
WHERE command != 'Sleep'
  AND id != CONNECTION_ID()
ORDER BY time DESC;
```

### 4.3 세션 상세 (SQL 전문) — MySQL 8.0+

PROCESSLIST에 세션 정보와 실행 쿼리(`info` 컬럼)가 함께 저장되어 있어 단일 조회로 끝납니다.

```sql
SELECT
    id AS session_id,                      -- 커넥션 ID
    user,                                  -- 계정
    host,                                  -- 접속 IP 및 포트
    db,                                    -- 현재 DB
    command,                               -- 실행 명령 유형
    state,                                 -- 현재 처리 상태
    time AS elapsed_sec,                   -- 실행 지속 시간(초)
    info AS sql_text                       -- 현재 실행 중인 전체 SQL
FROM performance_schema.processlist
WHERE command != 'Sleep'                   -- 대기 세션 제외
  AND id != CONNECTION_ID();
```

> MariaDB에서는 4.2와 마찬가지로 `information_schema.PROCESSLIST`로 바꿔 사용합니다.

### 4.4 Lock 모니터링 — MySQL 8.0+

`performance_schema`의 `data_lock_waits`와 세션 스레드 정보를 조인하여 대기 관계를 확인합니다.

> ⚠️ **2026-09-05 정정.** 원문 쿼리는 `data_lock_waits`에서 `requested_lock_mode` / `blocking_lock_mode`를
> 읽었는데 **그 뷰에는 두 컬럼이 없습니다** (MySQL 8.4.11 실행 시 `ERROR 1054 (42S22): Unknown column
> 'w.requested_lock_mode' in 'field list'`). 락 모드는 `data_locks` 쪽에 있으므로, 요청/블로킹
> `engine_lock_id`로 `data_locks`를 **각각** 조인해서 가져와야 합니다. 아래가 실행 검증된 쿼리입니다.

```sql
SELECT
    w_th.processlist_id                  AS waiter_session_id,
    w_th.processlist_user                AS waiter_user,
    w_th.processlist_host                AS waiter_host,
    w_th.processlist_time                AS wait_duration_sec,
    w_l.lock_mode                        AS requested_mode,
    CONCAT(w_l.object_schema, '.', w_l.object_name) AS target_table,
    LEFT(w_th.processlist_info, 300)     AS waiter_query,
    b_th.processlist_id                  AS blocker_session_id,
    b_th.processlist_user                AS blocker_user,
    b_l.lock_mode                        AS holding_mode,
    LEFT(b_th.processlist_info, 300)     AS blocker_query
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks w_l
    ON w_l.engine_lock_id = w.requesting_engine_lock_id
JOIN performance_schema.data_locks b_l
    ON b_l.engine_lock_id = w.blocking_engine_lock_id
JOIN performance_schema.threads w_th
    ON w_th.thread_id = w.requesting_thread_id
JOIN performance_schema.threads b_th
    ON b_th.thread_id = w.blocking_thread_id
ORDER BY w_th.processlist_time DESC;
```

`data_lock_waits`가 실제로 가진 컬럼은 다음과 같습니다 — 트랜잭션 ID(`*_ENGINE_TRANSACTION_ID`)와
락 ID(`*_ENGINE_LOCK_ID`), 스레드 ID(`*_THREAD_ID`)만 있고 **락 모드는 없습니다.**

```
ENGINE, REQUESTING_ENGINE_LOCK_ID, REQUESTING_ENGINE_TRANSACTION_ID, REQUESTING_THREAD_ID,
REQUESTING_EVENT_ID, REQUESTING_OBJECT_INSTANCE_BEGIN, BLOCKING_ENGINE_LOCK_ID,
BLOCKING_ENGINE_TRANSACTION_ID, BLOCKING_THREAD_ID, BLOCKING_EVENT_ID, BLOCKING_OBJECT_INSTANCE_BEGIN
```

간단한 조회용 내장 뷰도 있습니다.

```sql
SELECT * FROM sys.innodb_lock_waits;
```

### 4.5 Lock 모니터링 — MariaDB (또는 MySQL 5.7 이하)

InnoDB 표준 카탈로그(`information_schema`)를 활용해 대기 관계를 매핑합니다.

> ⚠️ **2026-09-05 정정.** 원문 쿼리는 `innodb_lock_waits`의 컬럼을 `requesting_lock_id`로 적었는데
> **실제 이름은 `requested_lock_id`입니다** (MariaDB 11.8.9 실행 시 `ERROR 1054 (42S22): Unknown column
> 'w.requesting_lock_id' in 'ON'`). 이 뷰는 트랜잭션 ID(`requesting_trx_id` / `blocking_trx_id`)도
> 함께 주므로, 원문처럼 `innodb_locks`를 거쳐 트랜잭션을 찾아갈 필요 없이 `innodb_trx`로 **바로**
> 조인하면 조인 수가 줄어듭니다. 락 모드·대상 테이블만 `innodb_locks`에서 `LEFT JOIN`으로 붙입니다
> (락 행이 그 사이 사라져도 대기 관계 자체는 남게 하려는 의도). 아래가 실행 검증된 쿼리입니다.

```sql
SELECT
    w_p.id                               AS waiter_session_id,
    w_p.user                             AS waiter_user,
    w_p.host                             AS waiter_host,
    w_p.time                             AS wait_duration_sec,
    w_l.lock_mode                        AS requested_mode,
    w_l.lock_table                       AS target_table,
    LEFT(w_p.info, 300)                  AS waiter_query,
    b_p.id                               AS blocker_session_id,
    b_p.user                             AS blocker_user,
    b_l.lock_mode                        AS holding_mode,
    LEFT(b_p.info, 300)                  AS blocker_query
FROM information_schema.innodb_lock_waits w
JOIN information_schema.innodb_trx w_t
    ON w_t.trx_id = w.requesting_trx_id
JOIN information_schema.processlist w_p
    ON w_p.id = w_t.trx_mysql_thread_id
LEFT JOIN information_schema.innodb_locks w_l
    ON w_l.lock_id = w.requested_lock_id
JOIN information_schema.innodb_trx b_t
    ON b_t.trx_id = w.blocking_trx_id
JOIN information_schema.processlist b_p
    ON b_p.id = b_t.trx_mysql_thread_id
LEFT JOIN information_schema.innodb_locks b_l
    ON b_l.lock_id = w.blocking_lock_id
ORDER BY w_p.time DESC;
```

`innodb_lock_waits`가 실제로 가진 컬럼은 네 개뿐입니다.

```
requesting_trx_id, requested_lock_id, blocking_trx_id, blocking_lock_id
```

> MySQL 8.0에서는 `information_schema.INNODB_LOCKS` / `INNODB_LOCK_WAITS`가 **제거**되었으므로 이 쿼리는 MySQL 8.0에서 동작하지 않습니다. 4.4를 쓰십시오.

## 5. MS SQL Server

### 5.1 세션 리스트

```sql
SELECT
    r.session_id,
    s.login_name,
    s.host_name,
    s.program_name,
    r.status,
    r.command,
    r.cpu_time,
    r.total_elapsed_time / 1000.0 AS duration_seconds,
    r.wait_type,
    r.wait_time,
    LEFT(t.text, 500) AS query_preview
FROM sys.dm_exec_requests r
INNER JOIN sys.dm_exec_sessions s
    ON r.session_id = s.session_id
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) t
WHERE s.is_user_process = 1
  AND r.session_id != @@SPID        -- 모니터링 세션 제외
ORDER BY r.total_elapsed_time DESC;
```

### 5.2 세션 상세 (SQL 전문)

특정 세션 클릭 시 팝업창용. 세션 정보를 담은 `sys.dm_exec_sessions`와 실행 요청을 담은 `sys.dm_exec_requests`를 조인하고, 동적 함수 `sys.dm_exec_sql_text`로 SQL 전문을 조회합니다.

```sql
SELECT
    s.session_id,                           -- 세션 식별자 (Oracle의 SID)
    s.login_name,                           -- 계정
    s.host_name,                            -- 접속 머신
    s.program_name,                         -- 클라이언트 프로그램
    r.status,                               -- 요청 상태
    r.total_elapsed_time / 1000.0 AS elapsed_sec,
    r.wait_type,                            -- 대기 이벤트
    t.text AS sql_text                      -- 현재 실행 중인 전체 SQL
FROM sys.dm_exec_sessions s
INNER JOIN sys.dm_exec_requests r
    ON s.session_id = r.session_id
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) t
WHERE s.is_user_process = 1
  AND s.session_id != @@SPID;
```

### 5.3 Lock 모니터링 (블로킹 체인)

```sql
SELECT
    wt.session_id                          AS waiter_session_id,
    s_w.login_name                         AS waiter_user,
    wt.wait_duration_ms / 1000.0           AS wait_duration_sec,
    wt.wait_type,
    LEFT(t_w.text, 300)                    AS waiter_query,
    wt.blocking_session_id                 AS blocker_session_id,
    s_b.login_name                         AS blocker_user,
    LEFT(t_b.text, 300)                    AS blocker_query
FROM sys.dm_os_waiting_tasks wt
INNER JOIN sys.dm_exec_sessions s_w
    ON wt.session_id = s_w.session_id
INNER JOIN sys.dm_exec_requests r_w
    ON wt.session_id = r_w.session_id
OUTER APPLY sys.dm_exec_sql_text(r_w.sql_handle) t_w
INNER JOIN sys.dm_exec_sessions s_b
    ON wt.blocking_session_id = s_b.session_id
LEFT JOIN sys.dm_exec_requests r_b
    ON wt.blocking_session_id = r_b.session_id
OUTER APPLY sys.dm_exec_sql_text(r_b.sql_handle) t_b
WHERE wt.blocking_session_id IS NOT NULL
  AND wt.blocking_session_id != 0;
```

> `total_elapsed_time`과 `wait_duration_ms`는 **밀리초** 단위라 `/ 1000.0`으로 초 변환이 필요합니다. PostgreSQL·MySQL과 단위가 다른 점에 주의하십시오.

> ⚠️ **2026-09-05 보완.** 5.3의 원문은 대기 세션의 요청(`r_w`)과 블로커 세션(`s_b`)을 `INNER JOIN`
> 하는데, **블로커가 트랜잭션만 열어둔 채 아무 요청도 돌리지 않는 경우가 실제 블로킹의 상당수**입니다
> (`BEGIN TRAN` 후 방치). `INNER JOIN`이면 그런 행이 통째로 사라져 "막혀 있는데 Lock 화면은 비어 있는"
> 상태가 됩니다. 구현에서는 `r_w` / `s_b` / `s_w`를 전부 `LEFT JOIN`으로 바꾸고, 블로커 상태는
> `COALESCE(r_b.status, s_b.status)`로 채웠습니다.

## 6. 대시보드에 추가해야 할 핵심 지표

실시간 DB 대시보드를 구성할 때 **Active Session**과 **Lock(블로킹 체인)** 외에 반드시 함께 올려두어야 하는 지표들입니다.

### 6.1 커넥션 풀 고갈율 (Connection Pool Usage)

WAS 커넥션 풀 누수나 트래픽 급증 시 서비스 장애로 직결되는 **1순위 지표**입니다.

- **표시 방식:** 게이지 차트 (현재 커넥션 수 / 최대 허용 커넥션 수)

| DBMS | 확인 대상 |
|---|---|
| PostgreSQL | `pg_stat_activity` 카운트 / `SHOW max_connections;` |
| MySQL / MariaDB | `Threads_connected` / `SHOW VARIABLES LIKE 'max_connections';` |
| MS SQL Server | `sys.dm_exec_connections` 카운트 / user options |

### 6.2 방치된 장기 트랜잭션 (Long-Running / Idle in Transaction)

락을 직접 걸지 않더라도 트랜잭션을 열어둔 채 방치하면 Undo/WAL/트랜잭션 로그가 정리되지 않아 **디스크 풀 장애**나 **테이블 블로트(Bloat)**를 유발합니다.

- **표시 방식:** 임계치(예: 60초 이상) 초과 트랜잭션 수치 및 경고 뱃지

| DBMS | 확인 대상 |
|---|---|
| PostgreSQL | `xact_start` 기준 경과 세션, 특히 `state = 'idle in transaction'` |
| MySQL / MariaDB | `information_schema.innodb_trx`의 `trx_started` 경과 시간 |
| MS SQL Server | `sys.dm_tran_active_transactions`, `sys.dm_tran_session_transactions` |

### 6.3 리플리케이션 지연 시간 (Replication / Standby Lag)

HA(고가용성) 이중화 구성이나 읽기 분산 복제본(Read Replica)을 둘 때 데이터 동기화 지연을 감지합니다.

- **표시 방식:** 지연 시간(초) 또는 바이트 단위 차이(Lag Size)

| DBMS | 확인 대상 |
|---|---|
| PostgreSQL | `pg_stat_replication`의 `write_lag`, `flush_lag`, `replay_lag` |
| MySQL / MariaDB | `SHOW REPLICA STATUS` (또는 `SHOW SLAVE STATUS`)의 `Seconds_Behind_Source` |
| MS SQL Server | Always On 환경의 `sys.dm_hadr_database_replica_states`의 `log_send_queue_size`, `redo_queue_size` |

### 6.4 버퍼 캐시 히트율 (Buffer Cache Hit Ratio)

쿼리가 메모리(Buffer Pool / Shared Buffers)에서 해결되는지, 물리 디스크 I/O를 일으키고 있는지 확인하는 지표입니다. **보통 95~99% 유지가 정상**입니다.

- **표시 방식:** 실시간 백분율(%) 트렌드 선 그래프
- **급감 시 의미:** 대량 풀스캔 쿼리 유입으로 기존 메모리 캐시가 밀려나 **디스크 I/O 병목**이 발생 중임을 의미

### 6.5 임시 공간 및 로그 용량 (Temp Space & Transaction Log)

정렬(`ORDER BY`, `GROUP BY`) 작업이 메모리를 초과해 디스크를 쓰거나, 대량 배치 작업으로 로그 영역이 차오르는 상태를 감지합니다.

| DBMS | 확인 대상 |
|---|---|
| PostgreSQL | `pg_stat_database`의 `temp_bytes`, `temp_files` |
| MySQL / MariaDB | `Created_tmp_disk_tables` (디스크 기반 임시 테이블 생성 수) |
| MS SQL Server | tempdb 여유 공간(`sys.dm_db_file_space_usage`), 트랜잭션 로그(`sys.dm_os_performance_counters`의 `Percent Log Used`) |

### 8.1 엔드포인트

| API | 대응 절 |
|---|---|
| `GET /api/rdb/session_list?db_id=&token=` | 3.1 / 4.1·4.2 / 5.1 |

조회 세 엔드포인트는 `authService.canAccessDb(token, db_id)`를 겁니다.
**`kill_session`만 `authService.isAdmin(token)` — 관리자 전용입니다.** 조회 권한과 같은 급으로 두면
"볼 수 있으면 죽일 수도 있는" 상태가 되는데, 세션 Kill은 남의 트랜잭션을 롤백시키는 파괴적 동작이라
분리했습니다(오라클 화면의 `kill_session`과 같은 기준). 화면에서도 Kill 버튼을 관리자에게만
보여주지만 그건 편의일 뿐이고, `sessionStorage`의 role은 브라우저에서 고칠 수 있으므로 **실제 차단은
서버에서만** 합니다.

`session_id`는 문자열로 받아 `Long.parseLong`으로 검증한 뒤 사용합니다 — 숫자가 아니면 DB까지 보내지
않고 `{"error":"세션 ID가 올바르지 않습니다."}`로 잘라냅니다. 조회 쪽은 `PreparedStatement`로
바인딩하지만, **Kill은 그럴 수 없어 이 검증이 유일한 방어선입니다**: MySQL의 `KILL`과 MS SQL의
`KILL`은 바인드 파라미터를 받지 못하는 명령이라 문자열로 조립할 수밖에 없습니다(PostgreSQL만
`pg_terminate_backend()`가 함수라 바인딩이 됩니다).

엔진별 Kill 명령:

| DBMS | 명령 | 비고 |
|---|---|---|
| MySQL / MariaDB | `KILL <id>` | `KILL QUERY`가 아니라 커넥션을 끊는다(오라클 kill과 같은 의미). 없는 세션이면 `ER_NO_SUCH_THREAD(1094)` |
| PostgreSQL | `SELECT pg_terminate_backend(<pid>)` | 대상이 없으면 **예외 대신 false** — 성공으로 세지 않도록 구분해야 함 |
| MS SQL Server | `KILL <spid>` | `ALTER ANY CONNECTION` 권한 필요. 시스템 세션(SPID ≤ 50)과 자기 자신은 불가 |

여러 건을 한 번에 보내며, 한 건이 실패해도 나머지는 계속 진행하고 건별 결과를 돌려줍니다.

```json
{"results":[{"session_id":50,"status":"killed","message":null},
            {"session_id":999999,"status":"error","message":"이미 종료된 세션입니다."}]}
```

### 8.2 응답 정규화

엔진마다 컬럼 이름도 단위도 다르므로(MS SQL만 밀리초, MySQL은 `program` 개념이 없음) 백엔드에서
공통 키로 정규화합니다. 덕분에 화면 코드(`rdb-session-views.js`)에는 `db_type` 분기가 한 줄도 없습니다.

- **세션 리스트**: `session_id`, `user`, `host`, `db`, `program`, `status`, `duration_seconds`, `wait_event`, `query_preview`
- **세션 상세**: `found`, `session_id`, `fields[{label,value}]`, `sql_text` — 항목이 엔진마다 다르므로 서버가 순서대로 내려주고 화면은 그대로 그립니다
- **Lock**: `waiter_session_id`/`waiter_user`/`waiter_host`/`waiter_query`, `wait_duration_sec`, `wait_type`, `blocker_session_id`/`blocker_user`/`blocker_host`/`blocker_state`/`blocker_query`

### 8.2-1 Lock 화면은 Holder/Waiter 트리로 그린다

백엔드는 위처럼 **"대기 1 : 유발 1" 쌍의 평평한 목록**을 주고, 트리는 화면(`rdb-session-views.js`)에서
쌍을 이어 붙여 만듭니다. 서버 쿼리를 늘리지 않고도 임의 깊이의 체인을 그릴 수 있습니다.

- **루트 = 아무도 기다리지 않는 세션 = 진짜 Holder.** 그 아래에 그 세션을 기다리는 Waiter를 붙입니다.
- A→B→C 다단계 체인이 그대로 중첩됩니다. 중간 노드는 `BOTH` 배지로 표시합니다(막고 있으면서 자신도
  기다리는 중).
- PostgreSQL은 `pg_blocking_pids()`가 배열이라 한 대기 세션에 유발 세션이 여럿일 수 있고, 그 경우
  같은 노드가 여러 부모 아래에 나타납니다.
- 서로가 서로를 기다리는 **순환**(교착 직전)이면 루트가 하나도 없습니다. 그대로 두면 화면이 비어
  "락이 없다"로 읽히므로, 가장 오래 기다린 세션을 임시 루트로 세우고 경고를 띄웁니다. 재귀는
  방문 경로로 끊습니다.

실측(PostgreSQL, 3단 체인 — 175가 182를, 182가 189를 막는 상황):

```
HOLDER 175   active                       BEGIN; UPDATE ... id=1; SELECT pg_sleep(400); COMMIT;
└─ BOTH 182  Lock / transactionid  58.64  BEGIN; UPDATE ... id=2; ... UPDATE ... id=1; COMMIT;
   └─ WAITER 189  Lock / transactionid  57.40  BEGIN; ... UPDATE ... id=2; COMMIT;
```

189를 Kill하면 182가 `BOTH` → `WAITER`로 자동으로 바뀝니다(더 이상 아무도 막지 않으므로).

### 8.3 문서 대비 구현에서 달라진 점

| 항목 | 이유 |
|---|---|
| MySQL/MariaDB 판정을 `db_type`이 아니라 **JDBC 메타데이터의 제품 버전 문자열**로 함 | `db_type`을 `mysql`로 잘못 등록한 MariaDB에 MySQL 전용 쿼리를 날리면 `ERROR 1146`으로 화면이 통째로 죽습니다. 메타데이터는 접속 시 이미 받아 둔 값이라 추가 쿼리가 없습니다 |
| 세션 리스트에서 `command = 'Daemon'`도 제외 (MySQL/MariaDB) | 안 빼면 `event_scheduler` 한 줄이 목록 맨 위에 상주해 실제 세션을 밀어냅니다 |
| PostgreSQL 세션 리스트에 `datname` 필터를 걸지 않음 | 인스턴스 전체의 활성 세션을 보는 화면이라, 다른 DB에서 도는 무거운 쿼리가 목록에서 사라지면 곤란합니다. 대신 `db` 컬럼으로 구분합니다 |
| PostgreSQL `client_addr`가 NULL이면 `'local'` | 빈 칸은 조회 실패처럼 보입니다 |
| 세션 상세는 유휴/자기 세션 필터를 걸지 않음 | 목록을 그린 뒤 클릭하기까지의 사이에 세션이 유휴로 바뀌었다고 "없음"으로 보이면 혼란스럽습니다. 실제로 종료된 경우만 `found:false` |
| MS SQL 상세는 `dm_exec_sessions` 기준 `LEFT JOIN` | 요청이 끝난 세션도 접속 정보는 보여주기 위함 |
| MS SQL 세션 리스트의 `status`에 `command`를 괄호로 덧붙임 | `suspended` 한 단어보다 `suspended (UPDATE)`가 훨씬 읽힙니다 |

### 8.6 용량 조회 (Oracle "테이블 스페이스 조회" 대응)

이 문서 범위 밖이지만 같은 화면에 함께 붙였습니다. Oracle은 **테이블스페이스 → 데이터파일** 2단인데,
RDB에는 테이블스페이스라는 단위가 없거나(MySQL/MariaDB) 기본 구성에서 하나뿐이라(PostgreSQL)
의미가 없어서, 같은 2단을 **"저장 단위 → 테이블"** 로 대응시켰습니다. DBA가 실제로 알고 싶은 것도
"어느 스키마/DB가, 그 안의 어느 테이블이 용량을 먹고 있나"입니다.

| API | 내용 |
|---|---|
| `GET /api/rdb/capacity?db_id=&token=` | 1단 — 저장 단위별 용량 |
| `GET /api/rdb/capacity_detail?db_id=&scope=&token=` | 2단 — 그 안의 테이블별 용량 |

| 엔진 | 1단 단위 | 조회 대상 |
|---|---|---|
| MySQL / MariaDB | 스키마 | `information_schema.schemata` + `tables` (data_length / index_length / data_free) |
| PostgreSQL | 스키마 (접속 DB 내) | `pg_class` + `pg_table_size()` / `pg_indexes_size()` / `pg_total_relation_size()` |
| MS SQL Server | 데이터베이스 | `sys.master_files`(할당) + 각 DB의 `dm_db_partition_stats`(사용) |

**할당·사용률은 MS SQL에서만 나옵니다.** 네 엔진 중 MS SQL만 Oracle처럼 데이터 파일을 미리 할당해
두고 그 안을 채워 쓰기 때문입니다. MySQL/PostgreSQL은 "할당" 개념이 없으므로 `total_mb`와
`used_pct`를 **null로 두고 화면에 `-`로 그립니다.** 억지로 채우면 안 됩니다 — 기존 DASHBOARD 탭의
Storage 패널은 `total==used, free=0`으로 채워서 **사용률이 항상 100%** 로 나오는데, 그건 정보가
아니라 잡음입니다.

MS SQL의 실제 사용량은 DB 안에 들어가야 볼 수 있어(`dm_db_partition_stats`는 DB 단위 DMV) DB마다
질의하면 왕복이 DB 수만큼 늘어납니다. 그래서 3-part naming으로 각 DB를 가리키는 SELECT를
`UNION ALL`로 이어 붙인 문장 하나를 만들어 한 번에 실행합니다. DB 이름은 `QUOTENAME()`으로 감싸고,
`HAS_DBACCESS`로 접근 가능한 DB만 넣습니다(없으면 권한 없는 DB 하나 때문에 문장 전체가 실패합니다).

`scope`(사용자가 고른 스키마/DB 이름)는 MySQL·PostgreSQL은 `PreparedStatement`로 바인딩하고,
MS SQL은 `sp_executesql` 파라미터로 넘겨 `QUOTENAME()`으로 감쌉니다. 실측으로
`scope=testdb]; DROP TABLE dbo.cap_test; --` 를 넣어 봤고, 0건 반환 + 테이블 20,000행 그대로
생존을 확인했습니다.

**이 탭은 Interval 자동 새로고침 대상이 아닙니다**(사용자 지시). 용량은 초 단위로 변하지 않는데
쿼리는 전 테이블의 크기를 훑어 무거워서, 주기적으로 돌려도 얻는 것이 없습니다. **탭을 열 때와
툴바의 `⟳ 새로고침` 버튼을 누를 때만** 다시 읽습니다. 세션 리스트/Lock 탭은 종전대로 Interval을
그대로 따릅니다.
