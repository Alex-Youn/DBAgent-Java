## 4. 오류 처리 기록 - 브라우저 캐시로 인한 "고쳤는데 안 바뀐다" 소동

배포 후 로그인하면 계속 옛 파일명(`fleet-overview-test-blue.html`)으로 리다이렉트되는 문제가 재현되어 원인 파악에 시간을 들였다.

1. **1차 오진**: dist/target 두 인스턴스가 동시에 포트 8006을 두고 기동되어 있던 걸 발견 - 이것도 실제 원인 중 하나였음(정리 후 재기동해도 증상 재현).
2. **진짜 원인**: `app.js?v=56`이라는 **정확히 같은 URL이 2026-08-25에 이미 다른 내용으로 쓰인 적**이 있어서, 브라우저 디스크 캐시가 그 옛 응답을 서버에 확인조차 안 하고 재사용(Ctrl+F5로도 재현) - Claude in Chrome으로 실제 브라우저에서 `fetch(url)`(기본 캐시)과 `fetch(url,{cache:'reload'})`(캐시 우회)의 응답을 직접 비교해서 확정했다.
3. **1차 대응**: `v=57`로 재부여(한 번도 안 쓰인 번호) → 해결되는 듯했으나, 캐시버스터가 없는 `fleet-overview.html` 자체도 같은 클래스의 문제를 겪음.
4. **근본 수정**: `com.dbagent.config.StaticResourceConfig`(`WebMvcConfigurer`) 신규 추가 - 모든 정적 리소스(`classpath:/static/**`)에 `Cache-Control: no-cache`를 강제해서, 브라우저가 매번 조건부 GET(If-Modified-Since)으로 재검증하도록 만듦. 파일이 실제로 바뀌었으면 반드시 새 응답을 받고, 안 바뀌었으면 여전히 304라 재다운로드 비용은 없음. `/api/*` 같은 `@RestController` 매핑은 이 리소스 핸들러보다 우선순위가 높아 영향받지 않는 것도 확인(`GET /api/login`→405, `GET /api/config`→200).

이 수정 이후로는 `?v=` 번호 재사용 충돌 문제가 재발하지 않을 것으로 기대됨. 자세한 진단 방법은 프로젝트 메모리(`build_environment.md`)에도 기록.

## 6. 커밋 전 코드 리뷰(`/code-review high`)로 발견/수정한 버그

- **v$version 조회 실패가 전체 상태 조회를 실패시킴**: 버전 코드네임 조회 쿼리가 기존 로직과 같은 try 블록 안에 있어서, v$version에 대한 권한이 없는 계정 등으로 이 쿼리 하나만 실패해도 CPU/MEM/세션 등 나머지 지표까지 전부 "DOWN"으로 오분류될 위험이 있었음 → 별도 try/catch로 격리해서 이 조회가 실패해도 나머지 지표는 정상 반환되도록 수정.
- **DOWN 전환 시 옛 버전 정보가 카드에 남는 버그**: 인스턴스가 alive였다가 down으로 바뀌면, 백엔드의 down 응답에 `version`/`versionCodename` 키 자체가 없어서 프런트(`Object.assign`)가 예전 폴링에서 받은 값을 지우지 않고 그대로 유지 - "연결할 수 없습니다" 배너 옆에 옛 "[Oracle 21c]" 태그가 그대로 남아있는 것처럼 보임 → down 응답에도 두 필드를 명시적으로 `null`로 채워서 프런트 병합 시 확실히 지워지도록 수정.
- **(수정 안 함) v$version이 매 폴링(기본 3초)마다 재조회됨**: 버전은 인스턴스 재기동 전까지 안 바뀌는 값이라 캐싱하면 더 효율적이지만, 이 앱은 v$instance 상태/uptime 등 다른 "안 바뀌는" 값들도 원래부터 매 폴링마다 그냥 재조회하는 설계라 - 굳이 이 필드만 별도 캐시 상태를 두는 게 기존 설계 일관성에 안 맞다고 판단해 그대로 둠. 인스턴스 수가 매우 많아지면 재검토.

두 프로젝트 모두 재빌드/재배포/재기동 후 다시 헬스체크(`index.html`/`fleet-overview.html` 200) 완료.

### 8-3. 실제 검증한 항목 (모두 정상 확인)

Oracle에 `LOCK TABLE ... IN EXCLUSIVE MODE`로 holder/waiter를 직접 만들어(TM Lock 시나리오) 아래를 전부 실제 세션으로 검증:

- 세션 TTL 자동정리: 40일 전 `created_at`을 가진 가짜 세션 삽입 → 조회 시점 필터링 즉시 거부(403) 확인, 정리 쿼리가 만료 세션만 정확히 삭제하는 것 확인, 임계치를 1일로 임시 조정해 실제로 반영되는 것까지 확인 후 30일로 원복
- Dashboard 장애발생 가능성 그래프의 숨은 "🚨 장애조치(Holder 세션 자동 Kill)" 버튼: 독립적인 TM Lock holder+waiter 쌍 6개를 만들어 80~90%까지 끌어올린 뒤 클릭 → holder 6개 전부 Kill되고 `v$lock`에서 TM Lock 0건으로 해제되는 것 확인
- Kill Session 체크박스(개별 + 전체선택) 4곳 전부: Dashboard Active Session, Current Session 메뉴, Lock Holder/Waiter Tree(TM Lock) 탭 - 실제 Oracle 세션으로 Kill 후 SID+SERIAL# 매칭으로 DB에서 사라진 것 확인
- SQL 정합성/튜닝 메뉴의 sLLM 미연동 안내 메시지 + "1차 성능점검"(실제 EXPLAIN PLAN) 정상 동작
- 다크모드 토글이 `location.reload()` 없이 `data-theme` 속성만 바꾸고 조회 중이던 결과를 유지하는 것 확인
- `databases.json` 중복 ID 수정 후 fleet_status에서 8개 DB 전부 고유 ID로 정상 조회되는 것 확인

## 9. ERD 다이어그램 텍스트 잘림 수정 (8-2에서 보류했던 이슈 재검토 후 해결)

8-2에서 "경미해서 보류"로 남겨뒀는데, 사용자가 저녁 세션에 다시 확인해서 진짜 원인을 찾아 수정했다.

### 9-1. 시행착오

1. **1차 시도(실패)**: `mermaid.initialize()`에 `er: { entityPadding: 30, minEntityWidth: 120 }`을 추가해 박스 여백을 넓힘 - 배포 후에도 "여전히 끝자리가 잘린다"는 재현 보고를 받음.
2. **2차 시도(실패)**: mermaid 내부적으로 박스 너비 계산에 쓴 값과 최종 svg `viewBox` 크기가 어긋나는 레이아웃 버그가 있을 것으로 추정, 렌더링 후 루트 `<g>`의 `getBBox()`를 다시 측정해 `viewBox`/`width`/`height`를 덮어쓰는 보정 로직을 추가 - 그래도 재현됨.
3. **진짜 원인 규명**: Claude in Chrome으로 실제 렌더링된 ERD의 DOM을 직접 까봄. 테이블명은 svg `<text>`가 아니라 `<g class="label"><foreignObject><div>TB_AP010</div></foreignObject></g>` 형태의 **HTML 라벨**로 그려지는데, mermaid가 이 `foreignObject` 자체의 폭을 실제 텍스트가 필요로 하는 폭(예: 70px)보다 좁게(63.25px) 계산해서 그 경계에서 글자가 잘리는 것이었음. 1·2차 시도는 둘 다 바깥쪽 rect나 svg 캔버스 크기를 건드린 것이라 이 foreignObject 자체의 폭 문제는 손대지 못해서 효과가 없었음.

### 9-2. 최종 수정 (`app.js`, `relation-search-btn` 클릭 핸들러 내 mermaid 렌더링 직후)

- `mermaid.init()` 렌더링 직후 모든 `<foreignObject>`를 순회하며 내부 `<div>`의 실측 폭(`scrollWidth`)이 foreignObject의 선언 폭보다 크면, foreignObject 폭을 늘리고 그 부모 `<g class="label">`의 `translate` 변환을 다시 계산해 가운데 정렬을 유지하며, 같은 엔티티의 `rect`(박스 테두리)도 함께 넓힘. 텍스트 실측 기반이라 테이블명이 몇 글자든 자동으로 대응됨.
- 그 위에 루트 `<g>`의 `getBBox()`로 svg `viewBox`/`width`/`height`를 재조정하는 보정(2차 시도 로직)도 안전망으로 유지 - 라벨/박스를 넓힌 뒤 svg 자체가 너무 좁아서 다시 잘리는 것까지 방지.
- **FOUC(깜빡임) 후속 수정**: 위 보정이 `setTimeout(..., 500)` 안에서 실행되다 보니, mermaid의 1차(잘린) 렌더링이 화면에 잠깐 보였다가 0.5초 뒤 정상 크기로 "덮어써지는" 깜빡임이 사용자에게 관찰됨. `.mermaid` 컨테이너를 처음엔 `opacity: 0`으로 숨겨서 렌더링하고, 위 보정이 모두 끝난 시점에만 `opacity: 1`로 페이드인(0.15s)하도록 수정 - 렌더링 실패 등 예외 상황에서도 컨테이너가 영영 안 보이는 채로 남지 않도록 `else`/`catch` 분기에도 강제로 다시 보이게 하는 안전망을 넣음.
- `entityPadding`/`minEntityWidth`(1차 시도)와 `viewBox` 재조정(2차 시도)은 근본 원인은 아니었지만 무해하고 추가 여유 폭으로 도움이 되므로 그대로 남겨둠.

### 9-3. 검증

Claude in Chrome으로 실제 브라우저에서 `admin`/`admin` 로그인 후 Table Parent/Child 관계 화면에서 `TB_AP010` 조회:

- 수정 전: ERD 박스에 "TB_AP01"(끝 글자 `0` 잘림) 확인 - foreignObject 폭 63.25px, 실제 필요 폭 70px으로 DOM에서 직접 확인.
- 수정 후: "TB_AP010" 전체가 잘리지 않고 표시됨(foreignObject 폭이 74px로 자동 확장된 것 확인).
- FOUC 수정 후: 조회 클릭 직후 `.mermaid` 컨테이너의 `opacity`가 `0`(숨김) → 보정 완료 후 `1`로 전환되는 것을 스크립트로 확인, 화면에는 잘린 박스 없이 완성된 박스만 페이드인으로 나타남.

`DBAgent-Java`(포트 8006 dist)에서 위 전 과정을 직접 재현·확인했고, `DBAgent-Java-AIX`도 동일한 수정을 포팅해 `mvn package` 빌드 및 `dist`(포트 8007)/`dist-aix` jar 교체까지 완료(AIX `dist` 인스턴스도 사용자가 직접 브라우저에서 재확인).
