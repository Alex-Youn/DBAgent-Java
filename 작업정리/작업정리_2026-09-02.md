## 2. WSL FastAPI 서버 기동 및 빌드/배포 시 발견한 이슈

- WSL(`~/llm_project`)에서 `serve/api_server.py`를 `setsid nohup ... & disown`로 기동, `/health`로 모델 로드 완료 확인.
- `build.ps1 -Dist` 실행 중 **기존 스크립트 버그 발견(미수정, 우회만 함)**: `dist\stop.ps1`이 내부적으로 `Set-Location $PSScriptRoot`를 호출해 PowerShell 세션의 현재 작업 디렉터리를 `dist\`로 바꿔버리는데, `build.ps1`의 `Copy-Item $jar $distJar` 줄이 `$jar`를 상대경로(`target\dbagent-java-0.1.0.jar`)로 참조하고 있어서 `dist\target\...`을 찾다가 실패함. 이번엔 `target\dbagent-java-0.1.0.jar`를 절대경로로 직접 `dist\`에 복사해서 수동으로 마무리(백업 `.bak`/`.bak2` 생성). **다음에 `build.ps1 -Dist`를 쓸 일이 있으면 `$jar`/`$distJar`를 절대경로(`Join-Path $PSScriptRoot ...`)로 바꿔야 근본 해결됨.**
- **실제 서빙 중이던 인스턴스는 `dist\`(포트 8006)였고 루트 `target\`은 dist와 포트가 겹쳐 기동 시 조용히 죽음**(에러 로그에도 안 남음) - 루트 `dbagent-java.pid`가 죽은 PID를 가리키던 stale 파일이라 삭제 처리. 앞으로 이 프로젝트를 재시작할 땐 실제 서빙 주체가 `dist\`라는 점을 기억할 것.
- 최종적으로 `dist\` 인스턴스를 재기동해 `POST /api/sqltuning/analyze`를 curl로 직접 호출, 실제 모델 응답을 받는 것까지 end-to-end 검증 완료 (원복 전까지 하루 종일 여러 차례 재검증).

## 3. Docker Oracle(테스트 DB) 권한/CDB-PDB 문제 발견 및 수정

SQL 정합성/튜닝 메뉴 테스트 중 학습 데이터 쿼리 실행 시 `ORA-00942: 테이블 또는 뷰가 존재하지 않습니다` 발생 - 조사 결과 근본 원인은 권한이 아니라 **접속 대상 컨테이너 착오**였음.

- Docker `oracle19c`(이미지 `gvenzl/oracle-xe:21-full`)는 CDB(멀티테넌트) 구조(`CDB$ROOT`/`PDB$SEED`/`XEPDB1`)인데, `C:/oracle_docker_data/tnsnames.ora`의 `ORCL`~`ORCL10` 별칭이 전부 `SID=XE`로 **빈 CDB 루트**를 가리키고 있었음. KIPOADM 스키마(테이블 2,495개, 시노님 176개, 8/26 실스키마 이식 완료분)는 **XEPDB1 PDB에만** 존재.
- `DBAGENT_USER`도 DBA 롤이 CDB 루트에만 부여돼 있고 XEPDB1엔 롤이 하나도 없었음(같은 계정명이라도 컨테이너별로 별개) - 그래서 CDB 루트로 붙으면 KIPOADM도 안 보이고 `dba_tables` 조회도 안 됐던 것.
- **조치**: (1) XEPDB1에서 `DBAGENT_USER`에 DBA/CONNECT/RESOURCE 재부여, 계정 잠금 해제. (2) `databases.json`(root/`dist` 둘 다) 전체 인스턴스의 `sid`를 `ORCL`~`ORCL10` → `XEPDB1`로 변경(TNS에 이미 정의돼 있던 올바른 별칭). (3) `dist\` 재기동 후 `/api/pool/test`로 정상 연결 확인.
- **KIPOADM 계정 활성화 및 시노님 생성**: KIPOADM 계정 잠금 해제, 비밀번호 `kipoadm`으로 설정. `TB_` 접두사 테이블 2,200건(전체 2,495건 중 백업/시스템성 295건 제외) 전부 `CREATE OR REPLACE PUBLIC SYNONYM SN_xxx FOR KIPOADM.TB_xxx`로 생성(예: `SN_AA001`↔`TB_AA001`). `apdba` 계정은 XEPDB1에 `CREATE SESSION` 권한조차 없어 로그인 자체가 안 되던 것을 추가로 발견해 `GRANT CONNECT`로 해결, 각 테이블 SELECT 권한도 2,200건 부여. `dbagent_user`/`apdba`/`kipoadm` 세 계정 모두 `EXPLAIN PLAN` 전체 사이클(PLAN_TABLE은 Oracle 기본 제공 퍼블릭 시노님이라 별도 생성 불필요, 이미 정상 동작 확인됨) 정상 동작 확인.
- **주의**: Oracle 21c부터 `SEC_CASE_SENSITIVE_LOGON` 파라미터 자체가 제거됨 - 비밀번호는 항상 대소문자 구분(우회 불가), 계정명(사용자명)은 대소문자 구분 안 함.

## 4. `DBAgent-Java-AIX` 포팅 (완료, 배포는 미완)

(2번 항목의 FastAPI 연동을 같은 날 `DBAgent-Java-AIX`에도 포팅함 - 단, 위 "원복" 결정 이후 이 포팅 결과물도 회사에 커밋하지 않고 로컬 보관만 함)

- `SqlTuningService`를 신규 작성 - AIX는 Java 8 고정이라 `java.net.http.HttpClient`(Java 11+) 대신 이미 있던 `OllamaChatService`와 동일 패턴(RestTemplate + `SimpleClientHttpRequestFactory`)으로 구현.
- `SqlTuningController`를 메인 프로젝트와 동일 로직으로 복원(`Map.of`/`String.isBlank` 대신 이 프로젝트의 Java 8 호환 헬퍼 `com.dbagent.util.Maps.of`/`Strings.isBlank` 사용, 기존 `SqlTuningRequest`/`SqlTuningAutoRequest`는 이미 레코드가 아닌 일반 클래스라 수정 불필요).
- `application.properties`에 `sqltuning.api.url`(기본값 `localhost:8010`)/`sqltuning.api.timeout-ms` 추가. **`dist-aix\`(실제 AIX 배포 대상)엔 지금까지 외부 설정 파일이 없었는데 이번에 신규 생성**해서 재빌드 없이 GPU 서버 주소를 바꿀 수 있게 함.
- `pom.xml`의 `maven.compiler.release=8` 강제 검증을 통과하는 빌드로 Java 8 API 호환성 확인, 로컬(port 8007)에서 WSL FastAPI 서버 대상 end-to-end curl 검증 완료.
- **미완(회사 정책과 별개로도 원래 남아있던 일)**: 실제 AIX 서버가 사내망에서 sLLM 서버(WSL/GPU)로 네트워크 도달 가능한지 미확인 - 배포 전 `curl <주소>/health`로 확인 필요.

## 5. New_sLLM 쪽 진행 상황 (요약 - 상세는 `New_sLLM\sLLM 구축 및 train 진행현황.md` 참고)

- 베이스 모델(파인튜닝 전, `Qwen2.5-Coder-7B-Instruct`) 75건 eval 최초 측정: **48.0%**(9개 카테고리는 이미 3/3, 10개 카테고리는 완전히 0/3 - Oracle 옵티마이저 특화 진단은 파인튜닝 없이는 전혀 안 됨을 수치로 확인).
- `bad_join_order` 카테고리가 4차례(실사례 데이터 기반 시도)나 개선에 실패해오다가, 실제 오답 사례(FK/참조무결성과 혼동)를 근거로 합성 대조학습 데이터 20건을 새로 생성 → continue-from-checkpoint 재학습 → **98.7%(74/75)로 프로젝트 최초로 챔피언을 실제로 넘음**. 새 챔피언: `v1213-continue-bjo-v3/checkpoint-9`.
