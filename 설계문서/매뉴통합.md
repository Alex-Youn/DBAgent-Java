# AI DBA 메뉴 통합 설계

> **상태**: 설계 확정, 구현 전 (2026-09-11 논의 정리)
> **방식**: (B) 실질적 통합 — 별도 최상위 메뉴를 없애고 AI DBA 화면 안에서 전환
> **진행 순서**: `DBAgent-Java` 먼저 구현·검증 → `DBAgent-Java-AIX` 포팅

---

## 배경

- AI DBA 챗봇과 SQL Tune Advisor는 **이미 같은 백엔드**를 쓴다. 둘 다 sqlrestapi의 `RAGController`를
  호출하고 `promptId`만 다르다(`chatbot` / `tuning`). 2026-09-11 멀티 프롬프트 구조(`PromptService`,
  `prompts/<promptId>.md`) 도입으로 **시스템 프롬프트를 여러 개 둘 수 있게 되면서** 통합이 가능해졌다.
- 최상위 메뉴에서 `SQL Tune Advisor`와 `SQL 정합성/튜닝`(자체 파인튜닝 sLLM, **전혀 다른 서버**)이
  나란히 놓여 이름이 혼동됐다. Tune Advisor를 AI DBA 안으로 넣으면 이 혼동이 자연히 해소된다.

## 1. 화면 구조

메뉴 진입 시 기본 화면은 **AI SQL Tunner**.

```
┌───────────────┬──────────────────────────────────────────────┐
│ 모델: qwen3-   │                                              │
│ coder:30b     │   [AI SQL 성능분석] [AI Current SQL 분석]      │ ← 탭은 여기만
│ OpenSearch ●  │  ──────────────────────────────────────────  │
├───────────────┤                                              │
│ AI SQL Tunner │                                              │
│ AI 챗봇        │              (선택된 화면 내용)                │
│ AI SQL 작성기  │                                              │
│ Regex 오류검색 │                                              │
└───────────────┴──────────────────────────────────────────────┘
   좌측 프레임                        본문
```

- 큰 항목 4개는 **좌측 프레임**(탭 아님)
- **탭은 AI SQL Tunner 하위에만** 2개
- 좌측 프레임 상단에 **사용 중인 모델 이름** 표시

### 최상위 메뉴 변화

| 메뉴 | 변화 |
|---|---|
| `AI DBA` | 내부 구조 재편 (아래 참고) |
| `SQL Tune Advisor` | **삭제** (AI DBA 안으로 흡수) |
| `SQL 정합성/튜닝` | 유지. 단 `1차 성능점검` 버튼은 AI DBA로 이동 → 자체 sLLM 분석 기능만 남음 |

## 2. 화면별 상세

### 2-1. AI SQL Tunner  *(기존 "SQL Tune Advisor" 개명)*

#### 탭 ① AI SQL 성능분석 — 기존 기능 그대로

사내 튜닝 사례를 RAG로 검색해 참고하며 분석. 현재 SQL Tune Advisor 화면을 그대로 옮긴다.
- 백엔드: sqlrestapi `/api/query`, `/api/query/stream` (`promptId=tuning`, `index=sql_tuning_cases`)

#### 탭 ② AI Current SQL 분석 — **신규**

**핵심 발상**: 쿼리와 실측 성능정보를 먼저 보여주고, **DBA가 분석이 필요한지 판단한 뒤에만** 모델에
던진다. 불필요한 LLM 호출을 막는 사람-개입(human-in-the-loop) 방식.

```
┌─ 계정 선택 (관리자 전용) ──────────────────┐
├─ 바인드 변수 패널 (쿼리에 :바인드 있을 때만) ──┤
├─ 입력: 쿼리 textarea ─────────────────────┤
│        [1차 성능점검]  [성능분석]            │
├─ 출력: 실행계획/실측통계 → (분석 시) 분석 결과 ─┤
└──────────────────────────────────────────┘
```

- **`1차 성능점검`**: 기존 `SQL 정합성/튜닝` 메뉴에서 **이 화면으로 이동**. 쿼리를 실제 실행해
  실행계획+실측 통계를 출력에 그대로 표시 (LLM 호출 없음, 기존 `/api/sqltuning/quick_check` 재사용)
- **`성능분석`**: 1차점검 결과(쿼리+바인드+실행계획+실측치)를 sqlrestapi로 보내 분석
  - 1차점검 결과가 **없으면 비활성**. (결과 없이 누르면 넘길 데이터가 없고, 쿼리 텍스트만으로 하는
    분석은 이미 탭 ①이 하는 일이라 중복)
  - 백엔드: sqlrestapi `/api/chat` + **신규 promptId `current-sql`** (RAG 검색 불필요 — 사례를
    찾는 게 아니라 눈앞의 실측치를 해석하는 작업)

**두 번째 입구 — 세션상세 `Tuning` 버튼**

실시간 세션 클릭 → 세션 상세 팝업의 `Tuning` 버튼도 이 탭으로 연결된다. 1차점검 흐름과 **같은 기능**의
다른 입구이며, 쿼리·바인드·성능정보가 미리 채워진 상태로 진입해 DBA가 판단 후 `성능분석`을 누른다.

> ⚠️ 현재 `openSqlTuningFromPopup(sql, hashValue, binds)`는 **Plan을 넘기지 않는다.** 세션상세 팝업엔
> 이미 Plan 탭이 있으므로, handoff에 Plan/성능정보도 함께 싣도록 확장 필요.

### 2-2. AI 챗봇 — 기존 기능 그대로

### 2-3. AI SQL 작성기 — **신규** (작업량 최대)

테이블/인덱스 구조를 DB에서 가져와 컨텍스트로 넘기고, 조건을 주면 SQL을 작성한다.

- 계정/DB 선택 필요 (`SQL 정합성/튜닝`의 계정 드롭다운과 동일 패턴)
- 테이블명 입력 → `조회` → `추가` 방식으로 **여러 테이블**을 컨텍스트에 누적 (조인 쿼리 대응)
- 생성된 SQL은 **실행 연동** (SQL 실행/1차점검으로 이어질 수 있게)
- 백엔드: sqlrestapi `/api/chat` + **신규 promptId `sql-writer`**

> ⚠️ 테이블·인덱스 구조 조회 기능이 **현재 코드에 없다.** 신규 백엔드 필요 (아래 5절).

## 3. 상태 표시 (좌측 프레임 상단)

**사용 중인 모델 이름만 표시**하고, 모델/Ollama 연결 상태는 **표시하지 않는다.**

| 항목 | 표시 | 근거 |
|---|---|---|
| 모델 이름 | ✅ | `/health`의 `llm_model` |
| OpenSearch 상태 | ✅ | `/health`의 `vector_db` — 실제 연결 확인값 |
| 모델/Ollama 연결 | ❌ **표시 안 함** | 현재 `/health`는 설정값을 echo할 뿐 Ollama를 확인하지 않음 → 거짓 초록불이 됨 |

- **AI DBA 메뉴 진입 시 1회 조회**, 폴링 없음
  (`app.js`의 `targetId === '...'` 분기에 `aidba` 추가 — 기존 패턴 그대로)
- 모델명은 **반드시 sqlrestapi에서 받아올 것.** 앱 설정에 중복 기재하면 `start_server_prod.sh`의
  환경변수 모델 교체(`qwen2.5-coder:3b` ↔ `qwen3-coder:30b`)와 어긋난다.
- `/health`는 내부적으로 타임아웃 없는 OpenSearch 확인을 수행하므로 **비동기 호출 + 실패 시 표시 생략**
  으로 처리한다.

## 4. 시스템 프롬프트 (총 4개 — 기존 2 + 신규 2)

| 화면 | promptId | 파일 | 상태 |
|---|---|---|---|
| AI SQL 성능분석 | `tuning` | `prompts/tuning.md` | 기존 |
| **AI Current SQL 분석** | `current-sql` | `prompts/current-sql.md` | **신규** |
| AI 챗봇 | `chatbot` | `prompts/chatbot.md` | 기존 |
| **AI SQL 작성기** | `sql-writer` | `prompts/sql-writer.md` | **신규** |
| Regex 오류검색 | — | — | LLM 미사용 |

- 초안: `prompts-draft/current-sql.md`, `prompts-draft/sql-writer.md`
- promptId는 `PromptService`의 `SAFE_ID`(`[a-zA-Z0-9_-]+`) 제약을 만족해야 한다.
- 프롬프트 파일은 mtime 기반 핫리로드라 **내용만 바꿀 땐 재기동 불필요**.

## 6. 구현 단계

1. **화면 재편** — 좌측 프레임 + AI SQL Tunner 하위 탭 2개, 기본 진입 AI SQL Tunner, 모델명 표시,
   `SQL Tune Advisor` 최상위 메뉴 제거
2. **AI Current SQL 분석** — 1차점검 버튼 이동, `성능분석` 버튼, 세션상세 handoff 확장, 프롬프트 ①
3. **AI SQL 작성기** — 스키마 조회 API + 다중 테이블 컨텍스트 UI + 프롬프트 ② + 실행 연동

각 단계 완료 후 `DBAgent-Java-AIX` 포팅 (Java 8 문법: `Strings.isBlank()`, `Maps.of()` 등).

## 7. 검토 중 확인된 기술 사항

- **화면 간 데이터 전달 메커니즘은 이미 존재한다.** 세션상세 팝업의 `jump-to-tuning-btn`이
  `window.opener.openSqlTuningFromPopup(...)`로 메인 화면 입력창을 채우는 방식이 동작 중
  (`app.js:3198`). 새로 설계할 필요 없이 목적지만 바꾸면 된다.
- **방화벽은 9300(sqlrestapi) 하나만 오픈.** OpenSearch(9200)·Ollama(11434)는 외부 접근 불가.
  단 **sqlrestapi는 같은 서버 안에서 둘 다 접근 가능**하므로 `/health` 한 번으로 OpenSearch 상태까지
  받아올 수 있다.
- **브라우저 → sqlrestapi 직접 호출 가능.** `RAGController`에 `@CrossOrigin(origins = "*")`가 이미
  있어 CORS도 막히지 않는다. 다만 프론트에 내려줄 주소는 **DBA 워크스테이션에서 닿는 주소**여야 하며
  (개발기의 `localhost:9300`과 다를 수 있음), UI에 HTTPS를 씌우면 mixed content로 차단된다.
- **실제 실행 경로는 SELECT/WITH만 허용된다** (`ExecutionPlanService:98`, 데이터 변경 방지).
  AI SQL 작성기의 생성 SQL 실행 연동도 이 제약을 따른다.

## 8. 나중에 (sqlrestapi 손볼 때)

- `OpenSearchSearchService.isConnected()`에 **타임아웃 추가** — 현재 `.block()` 무제한 대기라
  OpenSearch가 "응답 없음" 상태면 `/health` 자체가 멈춘다.
- 모델/Ollama 상태를 정말 보고 싶어지면 `/health`에 `GET localhost:11434/api/tags` 추가.
  한 번의 호출로 **Ollama 생존 + 해당 모델 존재 여부**를 동시에 확인할 수 있다.
  (`/api/ps`는 부적절 — keep-alive 만료 후 언로드가 정상이라 평소에 빨간불이 된다.)
