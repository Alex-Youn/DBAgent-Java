## 0. 요구사항 요약

"성능 이력 조회" 화면이 ASH(인메모리) + AWR(dba_hist) UNION 조회에 엄격한 튜닝 후보 필터를 얹고 있어 실제로 보이는 데이터가 거의 없고, 산점도 단일 차트라 시인성도 낮음. 이를 (1) 자체 시계열 적재, (2) SQL 텍스트 LIKE 검색, (3) 쿼리 타입 색상 구분, (4) 산점도 대체, (5) 항목 간 의존관계 정리 관점에서 검토. 폐쇄망(디스크/외부 라이브러리 제약) 및 AIX 이관본(H2) 동시 대응이 전제 조건.

### 1.1 "쓸만한 데이터가 없는" 원인은 하나가 아니라 4가지

**(원인 A) `exec_count >= 100` 필터가 사실상 "현재 공유풀 생존 SQL"만 통과시킴**

```sql
) sql_execs AS (SELECT sql_id, SUM(executions) as exec_count FROM v$sqlarea GROUP BY sql_id)
...
AND NVL(s.exec_count, 0) >= 100
```

`v$sqlarea`는 현재 시점의 공유풀 스냅샷. 과거 이력(특히 AWR 구간)의 sql_id가 이미 공유풀에서 aged out 되었거나 인스턴스가 재기동되었으면 `exec_count`가 0이 되어 `LEFT JOIN` + `>= 100` 조건에서 행이 통째로 사라짐. "오래된 이력일수록 더 많이 사라지는" 구조로, 이력 조회 화면의 목적과 정반대로 동작. 이 값은 "이 시간 구간의 실행 횟수"가 아니라 "인스턴스 기동 이후 누적"이라 의미적으로도 시간 필터와 맞지 않음.

**(원인 B) `duration >= 3` 필터 + `NVL(sql_exec_start, sample_time)` 조합의 전량 탈락**

```sql
ROUND((CAST(h.sample_time AS DATE) - CAST(NVL(h.sql_exec_start, h.sample_time) AS DATE)) * 24*60*60, 2) >= 3
```

`sql_exec_start`가 NULL인 샘플(SQL이 특정되지 않은 대기, 일부 재귀/백그라운드 성격 샘플 등)은 NVL에 의해 duration이 정확히 0이 되고, `>= 3` 조건에서 100% 탈락. NULL을 "모름"으로 두지 않고 0으로 만들어 버리는 바람에 "짧은 쿼리는 뺀다"가 아니라 "시작 시각을 모르는 샘플은 무조건 뺀다"가 되어 있음.

**(원인 C) ASH 인메모리 보존 한계 + AWR 밀도/라이선스**

`v$active_session_history`는 링버퍼라 바쁜 인스턴스에서는 수십 분~수 시간이면 롤오버됨. `dba_hist_active_sess_history`는 AWR이 ASH 샘플을 1/10로 솎아서 저장하므로 밀도가 1/10이고, 두 뷰 모두 Diagnostic Pack 라이선스 대상.

**(원인 D) UNION ALL 중복 가능성**

ASH 인메모리 버퍼에 남아 있으면서 이미 AWR로 flush된 샘플은 두 뷰 모두에 나타날 수 있어 같은 (sample_time, session_id, serial) 행이 2번 잡힐 수 있음. 산점도에서는 점이 겹쳐 보여 티가 안 나지만, 건수 기반 집계 차트로 바꾸면 곧바로 수치 왜곡으로 드러남.

> **시사점**: 원인 A, B, D는 저장소를 바꾸지 않고 쿼리만 고쳐도 해결되는 문제. 자체 적재(원인 C 대응)를 먼저 하면 공수가 훨씬 큰 일부터 하게 되므로, 검증 순서를 뒤집는 것을 권고(6절 참고).

### 1.3 이식성 제약 (반드시 설계에 반영)

원본은 SQLite, AIX 이관본은 H2. 이관본 `InstanceMetricHistoryService` 주석에 이미 겪은 3가지 함정이 기록되어 있음.
- `TEXT` → H2에서는 CLOB류로 매핑되어 PK/인덱스 불가 → `VARCHAR(n)` 사용
- `INTEGER` → H2는 32비트라 epoch millis 저장 불가 → `BIGINT` 사용
- `INSERT OR REPLACE`(SQLite 전용) → H2는 `MERGE INTO ... KEY(...)`

추가로 이번 설계에서 새로 문제가 될 항목 2가지:
- **LIKE 대소문자 동작이 다름.** SQLite의 `LIKE`는 ASCII 범위에서 기본 대소문자 무시, H2의 `LIKE`는 대소문자 구분. SQL 텍스트 검색을 두 환경에서 같게 동작시키려면 `sql_text_upper` 컬럼을 따로 저장하고 `UPPER(?)`로 비교하는 방식이 가장 안전(엔진 분기 불필요).
- **upsert 분기를 아예 없앨 수 있으면 없앨 것.** 신규 테이블은 PK 충돌이 정상 경로가 아니도록 설계하면(아래 3.2 참고) `INSERT OR REPLACE` / `MERGE` 분기 자체가 사라져 양쪽 포팅 비용이 줄어듦.

## 2. 항목 1 — 데이터 소스: 자체 적재가 타당한가

### 옵션 A. 쿼리/필터 개선만 (저장소 변경 없음)

원인 A/B/D를 제거. `v$sqlarea` 조인을 걷어내고(또는 표시용으로만 남기고 필터에서 제외), duration 임계값을 서버 고정값이 아니라 화면 입력값으로 빼고(기본 0 또는 1초), `sql_exec_start IS NULL`인 행은 duration을 NULL로 두어 필터에서 제외하지 않으며, UNION ALL 뒤에 (sample_time, session_id, serial) 기준 중복 제거를 넣음.
- 장점: 반나절~1일. 스키마/배포 리스크 없음. "데이터가 없다"의 체감 문제 대부분이 여기서 해결될 가능성이 높음. 조회 성능도 오히려 개선(v$sqlarea 전체 GROUP BY 제거).
- 단점: ASH 롤오버/AWR 밀도/라이선스(원인 C)는 그대로. 어제·지난주 조회는 여전히 AWR 의존.
- 적합 상황: 실측 결과 "필터만 풀어도 충분한 밀도가 나온다"면 이걸로 끝내도 됨.

### 옵션 B. Active Session 자체 적재 (instance_metric_history 패턴 확장)

10~20초 주기로 액티브 세션 목록을 전용 로컬 DB(`ash.db` / AIX는 `ash` H2 파일)에 적재하고, 이력 조회 화면이 원격 오라클 뷰 대신 이 테이블을 읽음.
- 장점: 보존기간을 통제(원인 C 해결). Diagnostic Pack 없는 사이트에서도(수집 모드를 `v$session`으로 두면) 이력 확보 가능 — 이게 이 옵션의 가장 큰 가치. 조회가 로컬이라 원격 DB에 부하를 주지 않고 빠름. AWR(1/10 솎음)보다 오히려 밀도가 높을 수 있음. 텍스트 검색(항목 2)·타입 색상(항목 3)의 토대가 됨.
- 단점: 디스크 증가(2.4절 산식 참고). 수집 실패/앱 정지 구간은 영구 공백(AWR은 앱과 무관하게 쌓임). 10~20초 주기라 그보다 짧은 쿼리는 통계적으로만 잡힘. 수집기 추가로 커넥션 풀 경합 위험(기존 60초 샘플러 대비 3~6배 빈도).
- 적합 상황: 옵션 A 실측 후에도 밀도가 부족하거나, Diagnostic Pack 미보유 사이트가 있는 경우.

### 옵션 C. 하이브리드 (권고)

조회 구간이 자체 수집 시작 시각 이후면 로컬 테이블을, 그 이전이면 기존 ASH/AWR 경로를 쓰고, 응답에 `source: "collected" | "ash" | "awr"` 플래그를 실어 화면에 "이 구간은 자체 수집 데이터입니다" 같은 표시를 함.
- 장점: 도입 첫날부터 화면이 비지 않음. 수집기가 죽어 있던 구간도 AWR로 메워짐. 기존 코드 경로를 지우지 않아 롤백이 쉬움.
- 단점: 두 경로의 컬럼/의미를 정규화하는 매핑 계층이 필요. 경계 구간에서 밀도가 달라 차트 모양이 튐(버킷 집계로 그리면 완화됨).

### 2.1 수집 모드는 두 가지, 용량 차이가 100배 이상

**모드 1 — `v$session` 스냅샷 (체크리스트 원문 그대로, 권고 기본값)**
매 사이클 `v$session`에서 `status='ACTIVE' AND type='USER'` 세션만 찍어 저장. 사이클당 행 수 = 그 순간 액티브 세션 수(보통 5~50). Diagnostic Pack 불필요. 화면 하단 "Active Session 리스트"와 컬럼이 1:1이라 UI 재사용이 쉬움. 단점은 20초보다 짧은 쿼리는 운 좋게 걸려야 잡힌다는 점.

**모드 2 — ASH delta 수집 (`sample_time > 마지막 수집 시각`)**
사이클마다 지난 N초의 ASH 1초 샘플을 전부 가져옴. 사이클당 행 수 = 액티브 세션 수 × N초. 20초 주기·평균 10세션이면 사이클당 200행으로, 모드 1 대비 20배. 초 단위 해상도라 짧은 쿼리도 놓치지 않지만 Diagnostic Pack이 필요하고 용량이 급증.

> 권고: 모드 1을 기본값으로 하고, 모드 2는 `dbagent.monitor.ash-collect-mode=session|ash` 프로퍼티로 선택 가능하게 두되 반드시 "duration >= 1초인 샘플만" 같은 필터를 함께 강제. 폐쇄망 운영 인스턴스에서 모드 2를 필터 없이 켜면 디스크가 며칠 만에 참.

### 2.2 스키마 초안

양쪽 엔진(SQLite/H2) 공통으로 쓸 수 있도록 `VARCHAR`/`BIGINT`/`DOUBLE`만 사용하고, upsert가 필요 없도록 PK를 잡음.

```sql
-- (1) 원시 샘플: 사이클 × 세션
CREATE TABLE IF NOT EXISTS ash_session_sample (
  instance_name   VARCHAR(64)  NOT NULL,   -- instance_metric_history와 동일 키 체계
  sampled_at      BIGINT       NOT NULL,   -- 사이클 대표 시각(epoch millis). 같은 사이클은 모두 동일 값
  sid             INTEGER      NOT NULL,
  serial_num      INTEGER      NOT NULL,
  sql_id          VARCHAR(13),
  sql_exec_id     BIGINT,                  -- 모드 2에서만 채워짐(실행 단위 구분용)
  sql_opcode      INTEGER,                 -- 항목 3(쿼리 타입 색상)의 원천
  plan_hash_value BIGINT,
  duration_sec    DOUBLE,                  -- sql_exec_start 기준. 모르면 NULL(0으로 채우지 말 것)
  event_name      VARCHAR(64),
  wait_category   VARCHAR(16),             -- getAshActivity()와 동일 CASE 결과(cpu/latch/user_io/...)
  session_state   VARCHAR(8),              -- ON CPU / WAITING
  db_user         VARCHAR(30),
  os_user         VARCHAR(30),
  program_name    VARCHAR(48),
  machine_name    VARCHAR(64),
  blocking_sid    INTEGER,                 -- 선택(락 분석용)
  PRIMARY KEY (instance_name, sampled_at, sid, serial_num)
);
CREATE INDEX IF NOT EXISTS idx_ash_sample_time    ON ash_session_sample (instance_name, sampled_at);
CREATE INDEX IF NOT EXISTS idx_ash_sample_sqlid   ON ash_session_sample (instance_name, sql_id, sampled_at);

-- (2) SQL 텍스트 사전: sql_id당 1행 (항목 2)
CREATE TABLE IF NOT EXISTS ash_sql_text (
  instance_name  VARCHAR(64)   NOT NULL,
  sql_id         VARCHAR(13)   NOT NULL,
  sql_text       VARCHAR(4000),
  sql_text_upper VARCHAR(4000),            -- 엔진 간 LIKE 대소문자 차이 흡수용
  sql_opcode     INTEGER,
  first_seen_at  BIGINT,
  last_seen_at   BIGINT,
  PRIMARY KEY (instance_name, sql_id)
);

-- (3) 장기 보존용 롤업: 5분 버킷 집계 (선택, 2.4 참고)
CREATE TABLE IF NOT EXISTS ash_sample_rollup (
  instance_name  VARCHAR(64) NOT NULL,
  bucket_at      BIGINT      NOT NULL,     -- 5분 버킷 시작 epoch millis
  wait_category  VARCHAR(16) NOT NULL,
  op_group       VARCHAR(16) NOT NULL,     -- select/insert/update/delete/plsql/ddl/other
  sample_count   INTEGER     NOT NULL,
  max_duration   DOUBLE,
  top_sql_id     VARCHAR(13),
  PRIMARY KEY (instance_name, bucket_at, wait_category, op_group)
);
```

설계 의도 3가지:
1. PK에 `sampled_at`을 넣어 upsert를 없앰. 사이클 대표 시각이 매번 달라지므로 정상 경로에서 PK 충돌이 없고, 따라서 `INSERT OR REPLACE`/`MERGE` 엔진 분기가 불필요(재시도 시에만 충돌하는데, `try/catch`로 삼기면 됨).
2. sql_text를 원시 샘플에 중복 저장하지 않음. 항목 2의 핵심 결정이며 용량 차이가 수백 배.
3. `duration_sec`는 NULL 허용. 현재 코드의 `NVL(...)→0→필터 탈락` 문제를 스키마 레벨에서 재발 방지.

### 2.3 저장소는 `metrics.db`가 아니라 새 파일로 분리 권고

이유 4가지:
1. 쓰기 빈도/행 수 차이가 두 자릿수 배수. `instance_metric_history`는 인스턴스당 사이클마다 12행(60초), 신규는 인스턴스당 사이클마다 수십 행(10~20초). 같은 파일에 넣으면 기존 대시보드 추이 차트 조회까지 같이 느려질 수 있음.
2. 보존/청소 정책이 다름. 지표는 30일 균일, ASH는 raw 단기 + 롤업 장기의 2단 정책.
3. SQLite `DELETE`는 파일 크기를 줄이지 않음. `auto_vacuum=INCREMENTAL`은 테이블 생성 전에 설정해야 효력이 있으므로, 이미 만들어진 `metrics.db`에는 적용할 수 없음. 새 파일이면 생성 시점에 `PRAGMA auto_vacuum=INCREMENTAL`을 걸고 청소 후 `PRAGMA incremental_vacuum`을 돌릴 수 있음. (AIX/H2는 2026-09-21 암호화 작업의 `DEFRAG_ALWAYS`/`SHUTDOWN DEFRAG` 전례 그대로 적용.)
4. 롤백이 파일 삭제 한 번.

설정 키 초안 (기존 네이밍 관례 유지):

```properties
dbagent.ash.datasource.url=jdbc:sqlite:db_config/ash.db?busy_timeout=5000
dbagent.ash.datasource.driver-class-name=org.sqlite.JDBC
dbagent.ash.datasource.hikari.maximum-pool-size=10
dbagent.ash.datasource.hikari.connection-init-sql=PRAGMA journal_mode=WAL

dbagent.monitor.ash-collect-enabled=false          # 기능 플래그. 배포는 off로, 검증 후 on
dbagent.monitor.ash-collect-mode=session           # session | ash
dbagent.monitor.ash-collect-interval-seconds=20
dbagent.monitor.ash-raw-retention-days=7
dbagent.monitor.ash-rollup-retention-days=90
dbagent.monitor.ash-collect-max-rows-per-cycle=500 # 폭주 방지 캡
```

### 2.4 샘플링 주기 / 보존기간 트레이드오프

행당 실질 크기(인덱스 2개 오버헤드 포함) 추정: SQLite 약 250B, H2 약 350~400B. 일일 용량 산식:

```
일일 바이트/인스턴스 = (86400 / 주기초) × 평균동시액티브세션수 × 250B
```

| 주기 | 평균 액티브 세션 | 일일/인스턴스 | 10인스턴스 × 7일 | 10인스턴스 × 30일 |
|---|---|---|---|---|
| 10초 | 10 | 21.6 MB | 1.5 GB | 6.5 GB |
| 20초 | 10 | 10.8 MB | 756 MB | 3.2 GB |
| 20초 | 30 | 32.4 MB | 2.3 GB | 9.7 GB |
| 30초 | 30 | 21.6 MB | 1.5 GB | 6.5 GB |
| 10초 | 50 (피크 상시) | 108 MB | 7.6 GB | 32 GB |

(모드 2 ASH delta는 위 값 × 주기초. 20초 주기·10세션이면 일일 216MB/인스턴스 — 필터 없이는 비현실적.)

권고안:
- 주기 20초 (체크리스트의 10~20초 중 보수적인 쪽). 10초는 용량이 2배인 데 비해 "1분 미만 쿼리 포착률"의 체감 개선이 크지 않음. 설정값으로 빼서 현장에서 조정 가능하게.
- raw 보존 7일, 5분 롤업 보존 90일. "어제 오후에 뭐가 느렸나"는 raw가 필요하고, "지난달 대비 추세"는 롤업이면 충분. 롤업은 5분 버킷 기준 인스턴스당 일 1~3MB 수준이라 90일도 부담 없음.
- 디스크 가드 필수. 청소 스케줄러(`@Scheduled(cron)`, 기존 `cleanupOldSamples()` 패턴)에서 파일 크기를 확인해 상한(`dbagent.monitor.ash-max-db-size-mb`, 예: 2048) 초과 시 보존일수와 무관하게 가장 오래된 날짜부터 삭제하고 WARN 로그. 폐쇄망은 디스크가 차면 앱이 죽고 원격 진단이 어렵기 때문에, 보존일수만 믿는 설계는 위험.
- 사이클당 행 수 캡(`ash-collect-max-rows-per-cycle`)도 필요. 장애 상황에서 액티브 세션이 수천 개로 튀는 순간이 정확히 수집이 가장 필요한 순간이자 디스크가 터지는 순간. duration 내림차순으로 상위 N행만 저장하고 초과분은 건수만 기록.

### 2.5 수집기 구현 시 주의점 (기존 사고 이력 기반)

- 기존 `InstanceMetricSamplerService`에 합치지 말고 별도 서비스로 분리. 주기가 다르고(60초 vs 20초), 한쪽 실패가 다른 쪽 사이클을 밀면 안 됨. 단 `SAMPLER_EXECUTOR`와 같은 "오라클 조회는 병렬, 로컬 DB 기록은 순차" 패턴은 그대로 따를 것 — 2026-09-18에 겪은 SQLite 경합 문제가 그대로 재현됨.
- 로컬 DB 기록은 반드시 `batchUpdate` + 단일 트랜잭션으로. 사이클당 수십~수백 행을 `jdbc.update()` 개별 호출로 쓰면 SQLite fsync가 행마다 발생해 20초 주기를 못 지킴.
- `setQueryTimeout`을 짧게(기존 `lockQueryTimeoutSeconds=3` 관례) 걸고, 실패는 삼키고 WARN만. 수집 실패가 다른 화면을 망가뜨리면 안 됨.
- 시각 기준을 명문화. `instance_metric_history`는 JVM epoch millis 사용. ASH 수집도 동일하게 JVM epoch로 통일 권고(조회 API 계약이 이미 그러함). 다만 `duration_sec` 계산은 DB 서버 시각 기준으로 오라클 쪽에서 계산해서 받아야 함 — 2026-09-22 타임존 9시간 어긋남 사고와 같은 계열의 함정.
- 기능 플래그 off로 배포 → 폐쇄망에서 하루 돌려보고 파일 증가량 실측 → on 순서 권고.

## 3. 항목 2 — SQL 텍스트 LIKE 검색

### 옵션 A. 조회 시점 실시간 `v$sqlarea` / `v$sql` LIKE
- 장점: 저장 0. 구현 1일 이내. 항상 최신.
- 단점: 공유풀에 남아 있는 SQL만 검색 가능 — "어제 그 느린 쿼리 찾기"라는 목적과 정면으로 어긋남. 원격 DB에서 `LIKE '%...%'` 풀스캔이 돌아 운영 인스턴스에 부하를 줌(`v$sqlarea`는 수만 행 규모일 수 있고 래치를 잡음). `v$sql_text`는 SQL을 64바이트 조각(piece)으로 쪼개 놓은 뷰라 조각 경계에 걸친 문자열은 LIKE로 못 찾음 — v$sql_text는 검색용으로 부적합.

### 옵션 B. 원시 샘플 행마다 sql_text 저장 후 LIKE
- 장점: 조인 없이 한 테이블에서 검색.
- 단점: 용량이 비현실적. 평균 SQL 텍스트 500B로 잡으면 2.4절 표의 "20초·10세션" 기준 일일 10.8MB → 약 32MB(3배)가 되고, 같은 SQL이 하루에 수천 번 중복 저장됨. LIKE 스캔 대상 행 수도 수백만 행이 되어 로컬 조회조차 느려짐.

### 옵션 C. sql_id 사전 테이블 분리 + 2단계 검색 (권고)

`ash_sql_text`에 sql_id당 1행만 저장하고, 검색은 ① 사전 테이블에서 텍스트 LIKE로 sql_id 집합을 뽑고 ② 그 집합으로 `ash_session_sample`을 시간 범위와 함께 조회하는 2단계로 수행.

```sql
SELECT s.* FROM ash_session_sample s
 WHERE s.instance_name = ? AND s.sampled_at BETWEEN ? AND ?
   AND s.sql_id IN (SELECT sql_id FROM ash_sql_text
                     WHERE instance_name = ? AND sql_text_upper LIKE ?)
 ORDER BY s.sampled_at;
```

- 장점: 용량이 sql_id 개수에 비례(수천~수만 행 × 평균 0.5KB = 수 MB~수십 MB). LIKE 스캔 대상이 수만 행뿐이라 SQLite에서 수십 ms 수준. 항목 3의 opcode도 여기 같이 보관해 재사용 가능. 검색 결과를 그대로 차트/리스트로 되돌릴 수 있음.
- 단점: 조인 한 단계 추가. 텍스트 수집 로직 필요.
- 텍스트 수집 방법: 수집기가 처음 보는 sql_id만 모아서 사이클 말미에 한 번 조회(메모리에 sql_id 캐시 유지). 사이클당 신규는 보통 0~수 건이라 부하가 거의 없음. 조회는 `SELECT sql_id, DBMS_LOB.SUBSTR(sql_fulltext, 4000, 1) FROM v$sql WHERE sql_id IN (...)` 형태로 `sql_fulltext`에서 4000자만 잘라 오는 것을 권고(`v$sqlarea.sql_text`는 1000자에서 잘려 검색 누락 생김). `IN` 목록은 1000개 제한이 있으니 분할.

### 비교

| 축 | A. 실시간 | B. 행마다 저장 | C. 사전 분리 |
|---|---|---|---|
| 과거 SQL 검색 | 불가 | 가능 | 가능 |
| 추가 저장량 | 0 | 매우 큼(raw의 3~4배) | 작음(수 MB~수십 MB) |
| 검색 속도 | 원격·느림·부하 | 로컬이나 대상 행 수 과다 | 로컬·빠름 |
| 운영 DB 부하 | 있음(v$ 풀스캔) | 수집 시 소량 | 수집 시 소량 |
| 구현 난이도 | 낮음 | 낮음 | 중 |

**권고: 옵션 C.** 다만 자체 적재(항목 1-B)가 미도입인 동안에도 "지금 돌고 있는 SQL 찾기" 용도로 옵션 A를 별도 기능(현재 세션 화면 쪽)으로 두는 것은 유용 — 두 기능은 목적이 다르므로 공존해도 혼란스럽지 않음.

부가 권고:
- 전문 검색(FTS) 도입은 권하지 않음. SQLite FTS5는 쓸 수 있어도 H2에는 동등 기능이 없어 양쪽 동작이 갈리고, 폐쇄망 라이브러리 추가 제약과도 충돌. 수만 행 LIKE 스캔으로 충분.
- `force_matching_signature`를 함께 저장해 두면(ASH/`v$sql` 모두 보유) 리터럴만 다른 동일 구조 SQL을 하나로 묶어 보여주는 기능으로 나중에 확장 가능. 컬럼 하나 추가 비용뿐이라 지금 넣어 두는 걸 권고.

## 4. 항목 3 — 쿼리 타입 색상 구분: 가능함

### 4.1 컬럼 확인 결과

Oracle 19c `V$ACTIVE_SESSION_HISTORY` 공식 문서로 확인.

| 컬럼 | 타입 | 내용 |
|---|---|---|
| `SQL_OPCODE` | NUMBER | SQL 명령 코드. `V$SESSION.COMMAND`와 동일 매핑 |
| `SQL_OPNAME` | VARCHAR2(64) | SQL 명령 이름(문자열) |
| `TOP_LEVEL_SQL_OPCODE` | NUMBER | 최상위 호출(예: PL/SQL 블록)의 opcode |
| `TOP_LEVEL_SQL_ID` | VARCHAR2(13) | 최상위 SQL ID |
| `IS_SQLID_CURRENT` | VARCHAR2(1) | 해당 SQL_ID가 실제 실행 중인지(Y/N) |

가능함. 이 앱은 이미 `getSessions()`에서 `v$session.command`를 `row.put("command", ...)`로 프런트에 내려주고 있음(`MonitorService.java` 218/254행). 프런트에 opcode → 이름 매핑 테이블을 만들면 성능 이력 화면과 현재 세션 화면이 같은 매핑을 공유할 수 있어 일관성 측면에서도 이득.

주의: `DBA_HIST_ACTIVE_SESS_HISTORY`에는 `SQL_OPCODE`는 있으나 `SQL_OPNAME`은 버전에 따라 없을 수 있음. 문자열(`SQL_OPNAME`)이 아니라 숫자(`SQL_OPCODE`) 기준으로 매핑해야 ASH/AWR/자체수집 세 경로가 같은 값을 냄.

### 4.2 매핑 방식

주요 코드(V$SESSION.COMMAND 기준): 1 CREATE TABLE, 2 INSERT, 3 SELECT, 6 UPDATE, 7 DELETE, 9 CREATE INDEX, 15 ALTER TABLE, 26 LOCK TABLE, 42 ALTER SESSION, 44 COMMIT, 45 ROLLBACK, 47 PL/SQL EXECUTE, 170 CALL METHOD, 189 MERGE.

전체 목록은 `AUDIT_ACTIONS` 뷰(`SELECT action, name FROM audit_actions`)에서 얻을 수 있음. 앱 기동 시 1회 조회해서 캐시하고, 권한 문제 등으로 조회가 실패하면 위 주요 코드 상수 맵으로 폴백하는 구조를 권고(폐쇄망에서 권한이 제한된 모니터링 계정일 가능성 대비).

### 4.3 색상 그룹 설계 (중요)

opcode를 그대로 색으로 매핑하면 수십 가지 색이 되어 오히려 시인성이 떨어짐. 6그룹 이하로 묶을 것.

| 그룹 | 포함 opcode | 비고 |
|---|---|---|
| SELECT | 3 | |
| INSERT | 2 | |
| UPDATE | 6 | |
| DELETE | 7 | |
| PL/SQL·기타 DML | 47, 170, 189(MERGE), 기타 DML | MERGE를 별도 색으로 뺄지는 현장 수요에 따라 |
| DDL·기타 | 1, 9, 15, 기타 / NULL | sql_id가 NULL인 샘플도 여기 |

설계상 짚어 둘 함정 3가지:
1. PL/SQL 블록 안의 SQL은 이중 구조. 블록 안에서 SELECT가 돌면 `sql_opcode=3`, `top_level_sql_opcode=47`. "이 시간대에 무슨 작업이 돌았나"를 보는 화면이므로 차트 색은 `sql_opcode`(실제 SQL) 기준으로 하고, 툴팁/상세에 "PL/SQL 호출 내부" 여부를 `top_level_sql_opcode=47`로 표시하는 조합을 권고.
2. `sql_opcode`가 NULL이거나 `IS_SQLID_CURRENT='N'`인 샘플이 존재하므로 "기타" 버킷은 필수. 이걸 빼면 또 다시 "데이터가 없다"가 재현됨.
3. 팔레트 충돌 피할 것. 좌측 Active Session Wait Class 차트가 이미 7색(cpu/latch/user_io/tx_lock/system_io/tm_lock/other)을 쓰고 있어, 같은 화면 계열에서 비슷한 색을 쓰면 "노란색이 CPU인가 SELECT인가" 혼동 생김. 명시적으로 다른 계열 팔레트를 쓰고, 가능하면 색 + 포인트 모양(또는 해칭) 이중 인코딩.

> 이 항목은 자체 적재 없이도 즉시 가능. 현재 `getHistorySessions()`의 SELECT 목록에 `h.sql_opcode`를 추가하고(ASH/AWR 양쪽 UNION 컬럼에 추가), 프런트에서 데이터셋을 그룹별로 분리하면 됨.

## 5. 항목 4 — 산점도 대체 차트

### 5.1 현재 산점도가 지고 있는 "기능 계약"

대안을 고를 때 지켜야 할 제약(`app.js` 4269~4437행):
- x = `capture_time`(시각), y = `duration_time`(초), 점 1개 = 샘플 1건
- 마우스 드래그 사각형으로 (시간 × duration) 2차원 선택 → `historyDataCache` 필터 → `showSelectedSessionsPopup()`
- 툴팁에 SID/Duration/SQL_ID
- 하단 테이블과 동일 데이터 공유

### 5.2 현재 방식에서 실제로 발생하는 시인성 문제

- 중첩(overplotting): 같은 초에 같은 duration을 가진 샘플이 완전히 같은 좌표에 찍혀 1건인지 50건인지 구분 불가. 단색(`#ffcc00`) + `pointRadius: 2` + 불투명이라 밀집 구간이 노란 덩어리가 됨.
- y축 극단값 지배: 3600초짜리 배치 1건이 들어오면 y축이 0~3600으로 늘어나 나머지 대부분(3~30초)이 바닥 1~2px에 깔림. 이게 "시인성이 나쁘다"의 가장 큰 원인일 가능성이 높음.
- 차원 낭비: 색·크기·모양이 전부 상수라 정보를 3개 더 실을 수 있는데 안 싣고 있음.
- 집계 부재: "몇 시쯤 가장 바빴나"를 점 밀도로 눈대중해야 함.
- 드래그 정밀도: 점이 겹치면 원하는 것만 고를 수 없음(1번째 그룹 3번 항목의 Top SQL 드래그 이슈와 같은 계열 문제).

### 5.3 대안

**옵션 1. 산점도 개선판 (버블 + 로그 y축 + 타입 색상)** — 최소 변경·즉효
- 핵심: `type: 'scatter'` 유지. ① y축을 `type: 'logarithmic'`으로(또는 이상치 클리핑 + 상단 별도 표기), ② 색 = 쿼리 타입 그룹(항목 3), ③ 점 반경 = 같은 좌표에 뭉친 샘플 수, ④ `backgroundColor`에 alpha 0.4~0.5 적용.
- 장점: 드래그/팝업 로직을 한 줄도 안 바꿔도 됨(데이터셋만 여러 개로 분리). 반나절~1일. 추가 라이브러리 없음. 로그 축만으로 시인성이 극적으로 개선.
- 단점: 밀집 자체는 완화될 뿐 해결은 아님. 로그 축은 사용자가 눈금을 오독할 수 있어 축 라벨을 "1s/10s/1m/10m"처럼 친숙하게 포맷해야 함.
- 적합: 지금 당장 체감 개선이 필요할 때. 사실상 무조건 먼저 하는 것을 권고.

**옵션 2. 시간 버킷 누적 막대 + 하단 상세 (메인 권고)**
- 핵심: 상단은 x=시간 버킷(1분/5분), y=샘플 수 또는 AAS, 색=쿼리 타입 그룹(또는 wait class)인 누적 막대. 드래그(또는 클릭)로 구간 선택 → 하단 테이블/팝업에 해당 구간 세션 목록.
- 장점: 시인성 최고 — "언제 바빴고 그때 무슨 유형이 돌았나"가 한눈에 들어옴. Chart.js 기본 기능(추가 라이브러리 0). 이미 만든 Active Session Wait Class 차트와 시각 언어가 통일되어 사용자가 새로 배울 게 없음. 항목 3(색 구분)과 자연스럽게 결합되고, 범례 클릭 필터링(1번째 그룹 6번 항목과 같은 요구)도 기본 제공. 중첩 문제가 원천적으로 없음.
- 단점: y축이 duration이 아니라 건수/AAS라 "제일 오래 걸린 쿼리 찾기"라는 원래 용도가 약화됨. 이 화면의 존재 이유가 그쪽이라면 단독 교체는 위험.
- 보완: 화면을 2층으로 — 상단 누적 막대(시간대 요약) + 하단 "선택 구간의 Top N 느린 세션" 테이블. OEM Top Activity, Grafana 대시보드가 쓰는 표준 패턴.

**옵션 3. 히트맵 (시간 버킷 × duration 버킷, 색 = 건수)**
- 핵심: x=시간 버킷, y=duration 구간(1s 미만/1~3s/3~10s/10~60s/1~5m/5m+), 셀 색 농도=건수. 셀 드래그 = 기존 2차원 선택 계약을 더 정확하게 유지.
- 장점: 중첩과 극단값 문제를 동시에 해결(구간화하므로 3600초 1건이 축을 지배하지 않음). "시간 × 소요시간" 2차원이라는 원래 의미를 보존. 밀도가 색으로 정량화됨.
- 단점: ① Chart.js에 matrix 컨트롤러가 기본 포함이 아니라 `chartjs-chart-matrix` 플러그인이 필요 — 폐쇄망 라이브러리 추가 제약과 충돌. 다만 `type:'scatter'`에 `pointStyle:'rect'` + 고정 `pointRadius` + 버킷 좌표를 주는 방식으로 추가 라이브러리 없이 유사 히트맵 구현이 가능하니 이 우회를 권고. ② 이상치 1건이 옅은 색으로 묻힘(색 스케일을 로그로 잡고, 최댓값 셀에 테두리 강조로 완화). ③ 버킷 경계 설계에 도메인 판단이 필요.
- 적합: 자체 적재로 데이터 밀도가 충분히 확보된 이후. 데이터가 성기면 히트맵은 빈 격자만 보여 오히려 초라해 보임.

**옵션 4(보조). 수평 간트/타임라인** — 세션별로 실행 구간을 선분으로 표시
- 장점: "오래 걸린 세션"을 선 길이로 직관적으로 보여줌. 겹치는 긴 쿼리들의 동시성이 드러남.
- 단점: 세션이 수백 개면 세로로 폭발. Top N(20~50)으로 제한해야만 쓸 수 있음. 구현 난이도 상.
- 적합: "느린 세션 Top N 상세" 전용 보조 뷰. 메인 차트로는 부적합.

### 비교

| 축 | 1. 산점도 개선 | 2. 누적 막대 | 3. 히트맵 | 4. 간트 |
|---|---|---|---|---|
| 시인성(밀집 시) | 중 | 상 | 상 | 중 |
| "느린 쿼리 찾기" 적합도 | 상 | 하 | 중 | 상 |
| 2D 드래그 계약 유지 | 그대로 | 시간축만 | 유지(더 정확) | 시간축만 |
| 추가 라이브러리 | 없음 | 없음 | 우회 필요 | 없음(구현 비용 큼) |
| 기존 화면 일관성 | 그대로 | 상(wait class 차트와 통일) | 중 | 하 |
| 데이터 밀도 요구 | 낮음 | 중 | 높음 | 낮음 |
| 구현 시간 | 0.5~1일 | 2~3일 | 3~4일 | 4일+ |

**권고: 옵션 1 → 옵션 2(2층 구조) 순으로 단계 적용, 옵션 3은 자체 적재 이후 선택.**

최종 화면 권고 구조:

```
[상단] 시간 버킷 누적 막대 (색 = 쿼리 타입 그룹, 범례 클릭 필터)  ← 옵션 2
         ↓ 드래그로 시간 구간 선택
[중단] 선택 구간의 산점도(로그 y축, 타입 색상, 버블)              ← 옵션 1 (기존 2D 드래그 계약 유지)
         ↓ 드래그로 (시간 × duration) 선택
[하단] 세션 목록 테이블 / 기존 팝업                                ← 현행 유지
```

이 구조면 기존 드래그·팝업 코드를 버리지 않으면서, "언제 바빴나 → 그중 뭐가 느렸나 → 그 세션 상세"라는 자연스러운 드릴다운이 만들어짐. 1번째 체크리스트 그룹의 3번(드래그 정밀도)·6번(색 계열 클릭 필터링) 요구와도 설계가 맞물림.

## 6. 항목 5 — 의존관계

### 6.1 결론: 1번은 나머지의 선행 조건이 아님. 단, "1번 중 어느 옵션이냐"가 갈림길.

| 항목 | 1-A(쿼리 개선) 의존 | 1-B(자체 적재) 의존 | 단독 구현 가능? |
|---|---|---|---|
| 2. SQL 텍스트 검색 | 무관 | 선택적 — 실시간 v$sqlarea 버전은 독립, "과거 SQL 검색"은 1-B 필요 | 예(축소 기능) |
| 3. 쿼리 타입 색상 | 무관 | 불필요 — `sql_opcode` 컬럼 추가만으로 가능 | 예(완전) |
| 4. 차트 교체 | 사실상 필요 — 데이터가 성기면 어떤 차트도 초라함 | 불필요 | 예(단, 1-A 선행 권장) |

의존 그래프:

```
1-A (필터/쿼리 개선)  ──┬──> 4 (차트 교체)        : 밀도가 있어야 차트가 의미 있음
                        └──> 3 (타입 색상)        : 색으로 나눌 데이터가 있어야 함
3 (sql_opcode 확보)   ─────> 4의 "색 구분" 부분   : 색상 인코딩의 데이터 원천
1-B (자체 적재)       ──┬──> 2 (과거 SQL 검색)    : 과거 텍스트는 적재해야만 존재
                        ├──> 4의 히트맵 옵션      : 고밀도 데이터 필요
                        └──> (장기 보존/라이선스 비의존)
2의 실시간 버전       ─────> 독립                 : 어디에도 의존 안 함
```

### 6.2 권장 구현 순서

| 단계 | 내용 | 예상 공수 | 비고 |
|---|---|---|---|
| 0 | 실측: 같은 시간 구간을 필터 유/무로 조회해 건수 비교 | 0.5일 | 1-B 필요성 자체를 판정하는 근거 |
| 1 | 1-A: exec_count 필터 제거, duration 임계 UI화, NVL 문제 수정, UNION 중복 제거 | 0.5~1일 | 즉효·저위험 |
| 2 | 3: `sql_opcode` 컬럼 추가 + opcode→그룹 매핑 + API 필드 | 1일 | 자체 적재 불필요 |
| 3 | 4-①: 산점도 개선(로그축/색/버블/알파) | 0.5~1일 | 드래그 로직 무변경 |
| 4 | 4-②: 상단 누적 막대 + 2층 드릴다운 구조 | 2~3일 | 여기서 화면 체감이 결정됨 |
| 5 | 2(실시간판): 현재 세션 화면 쪽 SQL 텍스트 검색 | 1일 | 선택 |
| 6 | 1-B: 자체 적재(전용 DB + 수집기 + 보존/청소 + 디스크 가드) | 4~6일 | 플래그 off 배포 → 실측 → on |
| 7 | 2(적재판)으로 승격 + 4-③ 히트맵 | 2~3일 | 6 완료 후 |

**1~4단계(총 4~6일)만으로 체감 문제의 대부분이 해소될 것으로 봄.** 6단계(자체 적재)는 "장기 보존"과 "Diagnostic Pack 비의존"이라는 별개의 가치를 위해 하는 일이므로, 0단계 실측 결과를 보고 우선순위를 재판단.

## 7. 권고안 요약

1. **항목 1** — 옵션 C(하이브리드)를 최종 목표로 하되, 착수는 옵션 A(쿼리 개선)부터. 현재 "데이터 없음"의 상당 부분은 저장소 문제가 아니라 필터/NVL 문제. 자체 적재는 전용 `ash.db`(AIX는 H2 별도 파일)로 분리, 기본 20초 주기 · `v$session` 스냅샷 모드 · raw 7일 + 5분 롤업 90일 · 디스크 상한 가드 · 기능 플래그 off 배포.
2. **항목 2** — sql_id 사전 테이블(`ash_sql_text`) 분리 + 2단계 검색. 행마다 sql_text를 저장하는 안은 용량상 기각. `sql_text_upper` 컬럼으로 SQLite/H2 LIKE 차이를 흡수. FTS는 도입하지 않음.
3. **항목 3** — 가능함. ASH/AWR 모두 `SQL_OPCODE` 보유(=`V$SESSION.COMMAND` 매핑, 앱이 이미 쓰는 값). 6그룹 이하로 묶고, PL/SQL 이중 구조와 NULL 버킷을 반드시 처리. 자체 적재 없이 즉시 구현 가능.
4. **항목 4** — 산점도를 버리지 말고 "상단 누적 막대 + 중단 개선 산점도 + 하단 목록"의 2~3층 드릴다운으로. 즉효는 로그 y축 + 타입 색상 + 알파(반나절). 히트맵은 데이터 밀도 확보 후.
5. **항목 5** — 3번은 완전 독립, 2번은 축소판으로 독립 가능, 4번은 1-A 선행 권장, 1-B는 2번 완전판과 4번 히트맵의 선행 조건.

## 8. 다음 단계 — 구현 전에 검증해야 할 가정

**반드시 폐쇄망 실측이 필요한 3가지**
1. 필터 제거 시 건수: 동일 시간 구간에 대해 `exec_count>=100`, `duration>=3`을 각각 뺐을 때 행 수가 얼마나 늘어나는지. 이 숫자 하나로 1-B 착수 여부가 결정됨.
2. 평균 동시 액티브 세션 수 분포: 2.4절 용량표의 유일한 입력 변수. 기존 `instance_metric_history`의 `db_time_aas`(=Average Active Sessions) 값이 이미 쌓여 있으므로 새로 측정할 필요 없이 조회만 하면 됨. 피크값 기준으로 잡을 것.
3. 디스크 여유 및 Diagnostic Pack 라이선스 보유 여부: 후자가 없으면 자체 적재는 "있으면 좋은 것"이 아니라 유일한 이력 수단이 되어 우선순위가 완전히 달라짐.

**오케스트레이터 확인이 필요한 의사결정 2가지**
4. 현재의 `exec_count>=100 AND duration>=3` 필터가 의도된 스펙(= 이 화면은 "튜닝 후보 전용")인지, 아니면 관성으로 남은 것인지. 전자라면 필터를 없애는 대신 "튜닝 후보만 보기" 체크박스로 UI에 노출하는 방식을 권고.
5. 이 화면의 1순위 용도가 "느린 쿼리 찾기"인지 "시간대별 부하 파악"인지. 전자면 산점도 계열 유지가 맞고, 후자면 누적 막대를 메인으로 올려야 함(5.3 옵션 2의 단점 참고).

**구현 시 사고 재발 방지 체크리스트**
- 신규 테이블은 `VARCHAR`/`BIGINT`만, upsert 없는 PK 설계로 SQLite/H2 분기 최소화
- 로컬 DB 기록은 `batchUpdate` 단일 트랜잭션, 오라클 조회는 `SAMPLER_EXECUTOR` 병렬
- 수집 쿼리에 `setQueryTimeout` 3초, 실패는 삼키고 WARN
- wait class 분류 CASE는 `getAshActivity()`·기존 샘플러와 문자 단위로 동일하게 복사(`system_io` vs `sys_io` 키 불일치로 이미 한 번 버그가 났던 지점)
- SQLite `auto_vacuum=INCREMENTAL`은 첫 테이블 생성 전에 설정(= 새 파일이어야 함), H2는 `DEFRAG` 전례 활용
- 기능 플래그 off 배포 → 폐쇄망 1일 실측(파일 증가량, 사이클 소요시간) → on
- 원본/AIX 동시 포팅 원칙에 따라 두 프로젝트 모두 같은 커밋 단위로 반영

## 9. 방향 전환 확정 (2026-09-24, 오케스트레이터 결정)

**메뉴명 변경 확정**: "성능 이력 조회" → **"성능 분석"**. 산점도 기반 "이력 조회"에서 wait class/event 드릴다운 기반 "분석" 화면으로 성격이 바뀐 것을 반영. 이후 이 문서 및 관련 문서에서 화면을 지칭할 때 "성능 분석"으로 표기.

위 설계 검토 이후 오케스트레이터가 화면의 근본 용도를 재정의함. 기존 산점도(개별 느린 쿼리 찾기)는 "업무 관련 여부와 무관하게 그냥 느린 쿼리만 나열"되어 실질적인 성능 분석에 도움이 안 된다는 지적. 대신:

- **핵심 방향**: "성능 이력 조회" 화면을 산점도 기반에서 **Current Session 매뉴의 Active Session Wait Class 그래프를, 과거 임의 구간에 대해 보여주는 방식**으로 전환. 즉 5.3절 "옵션 2(시간 버킷 누적 막대)"를 채택하되, wait class 기준(이미 만든 Active Session Wait Class 차트와 동일 색상/카테고리 체계 — cpu/latch/user_io/tx_lock/system_io/tm_lock/other)으로 구성. 항목 3(쿼리 타입 색상)에서 검토한 select/insert/update/delete 그룹보다 **wait class 축이 우선**.
- **드래그 기능 유지**: 그래프 위 드래그로 시간 구간 선택 → 해당 구간의 세션 상세내역을 팝업으로 표시하는 기능은 그대로 유지(기존 `scatterPointerToLocal`/드래그-브러시 계약 재사용).
- **하단 구성 확정(2026-09-24, 오케스트레이터 추가 제안)**: 애초 구상했던 "선택 구간의 느린 세션 목록"(개별 세션 플랫 리스트)을 **이벤트별 막대 그래프**로 대체. 상단 wait class 그래프와 **같은 선택 구간** 기준으로, 하단은 그 구간에 나타난 개별 event(예: "db file sequential read", "enq: TX - row lock contention" 등, wait_category보다 한 단계 세분화된 원본 event명) 별로 막대 그래프를 그리고, **막대 클릭 시 해당 이벤트의 세션 목록을 팝업으로 표시**. Oracle AWR "Top Timed Events" 리포트와 같은 패턴으로, "개별 세션 나열"보다 "이 구간에 뭐가 병목이었나"를 바로 파악하게 해줌 — 업무 관련성과 무관하게 그냥 느린 세션만 나열되던 기존 문제를 구조적으로 해결.
  - 최종 3단 드릴다운: **상단(시간대별 wait class 막대, 드래그로 구간 선택) → 하단(선택 구간의 event별 막대) → 막대 클릭(해당 event의 세션 목록 팝업)**.
  - 하단 event 막대는 `v$active_session_history.event`(원본 이벤트명)를 상단의 wait_category CASE보다 한 단계 안 풀어서 집계하면 됨 — 같은 원본 데이터(ASH/AWR)에서 파생 가능, 별도 데이터 소스 불필요.
- **팝업 통일**: 이벤트 막대 클릭 시 뜨는 세션 목록 팝업을 포함해 **환경설정 팝업을 제외한 모든 팝업**을 체크리스트 4번째 그룹 1~3번 내용(초기 크기 90%→80%, 세로형→가로형 통일, 세션 상세정보 표 재구성+문구 변경+탭 구성)으로 통일하기로 확정. 즉 4번째 그룹과 2번째 그룹 작업이 서로 연결됨 — 팝업 관련 작업을 동시에 처리해야 함.

### 9.1 기술적 영향

- **데이터 소스**: 과거 임의 구간(예: "지난주 화요일 오후 2~4시")을 보려면 `getAshActivity()`(현재는 `v$active_session_history`만, "최근 N분"만 조회)를 확장해서 시작/종료 시각을 입력받고, ASH 인메모리 보존기간을 벗어나는 구간은 `dba_hist_active_sess_history`(AWR)까지 같은 CASE 로직으로 버킷팅해야 함. **1절의 원인 C(ASH 롤오버, AWR 보존기간·Diagnostic Pack 라이선스)가 그대로 적용됨** — AWR 보존기간보다 오래된 구간이나 Diagnostic Pack 미보유 사이트는 이 방식만으로 과거 데이터 확보 불가, 그 경우 2절의 자체 적재(1-B)가 필요.
- **항목 2(SQL 텍스트 검색)/항목 3(쿼리 타입 색상)의 위치**: 메인 축이 wait class로 정해졌으므로, 쿼리 타입 색상 구분(항목 3)은 하단 "느린 세션 목록"에서 개별 세션 정보로 노출하는 보조 역할로 축소됨. SQL 텍스트 검색(항목 2)도 하단 목록에서 세션 상세 조회 시 필요한 보조 기능으로 위치가 정리됨 — 두 항목 모두 폐기가 아니라 "메인 그래프가 아니라 하단 목록/상세팝업의 부속 기능"으로 역할 재조정.
- **드래그-팝업 계약**: 기존 산점도의 2차원(시간×duration) 드래그가 아니라, wait class 막대 그래프이므로 **시간축 1차원 드래그**로 단순화됨(5.3절 옵션 2와 동일한 제약). 이는 기존 Active Session Wait Class 실시간 차트가 아직 세로 구간(시간) 드래그만 지원하는 것(체크리스트 1-3)과 일관되게 맞아떨어짐 — 오히려 1-3(좌측 그래프 드래그 미구현) 항목과 이 작업을 같이 처리하면 코드 재사용 가능.
- **팝업 통일(4번째 그룹)과의 결합**: 드래그로 뜨는 세션 상세 팝업이 4-3(세션 상세정보 표 재구성: SID.SPID/Serial Number/Program/Machine, OS User/DB User/Command/Status, Module/Logon Time/SQL ID/Hash Value 3x4 표 + SQL Text/DBMS Plan/Bind Variable 탭)과 4-2(팝업 모양 세로→가로 통일)의 **첫 적용 대상**이 됨. 즉 이 화면을 만들 때 팝업을 4번째 그룹 스펙대로 새로 만들면, 다른 화면의 팝업 통일 작업(4-2 범위 파악)의 레퍼런스 구현이 될 수 있음.

### 9.2 재정리된 착수 우선순위 (9절 반영)

1. `getAshActivity()` 확장: 시작/종료 시각 파라미터화 + AWR 폴백 (원인 C 재확인 필요 — 8절 실측 3번 항목과 연결)
2. wait class 히스토리 막대 그래프 프런트 구현 (Active Session Wait Class 차트와 시각 언어 통일) — 상단
3. 시간축 드래그 → 구간 선택 (1-3의 좌측 그래프 드래그 미구현과 동시 처리 고려)
4. 선택 구간의 **event별 막대 그래프** 구현 — 하단, 같은 선택 구간 기준으로 원본 event명 단위 집계(9절 하단 구성 참고)
5. event 막대 클릭 시 뜨는 세션 목록 팝업을 4번째 그룹 스펙(4-1/4-2/4-3)으로 신규 제작 — 팝업 통일의 첫 사례, 아래 9.3절 필드셋 반영
6. (필요 시) 1-B 자체 적재 — 8절 실측 결과 AWR 보존기간/라이선스가 부족하다고 판단될 때만

### 9.3 세션 조회 목록 필드 통일 (2026-09-24, 오케스트레이터 지적 + 확정)

Dashboard와 Current Session 매뉴의 Active Session 목록은 같은 `getSessions()`를 공유해 필드가 동일하지만, 성능 이력 조회(`getHistorySessions()`)는 필드 구성이 다름을 확인:

- **getSessions() (Dashboard + Current Session 공통, 18개 필드)**: db_name, status, sid, serial, server_pid, machine_name, username, program_name, duration_time, session_wait_pct, sql_id, event_name, plan_hash_value, sql_text, has_transaction, command, osuser, capture_time
- **getHistorySessions() (성능 이력 조회, 11개 필드)**: sid, serial, sql_id, event_name, capture_time, duration_time, program_name, osuser, plan_hash_value, exec_count, db_name

`status`, `server_pid`, `machine_name`, `username`, `session_wait_pct`, `sql_text`, `has_transaction`, `command`가 이력 조회 쪽엔 없고, `exec_count`만 추가로 있음.

**확정 방향(오케스트레이터)**: Lock Holder/Waiter Tree(별도 트리 구조 데이터라 목록형이 아니므로 제외)를 제외한 모든 세션 조회 목록의 필드 구성을 일관되게 통일.
- **`status`/`session_wait_pct`/`has_transaction` 3개는 성능 이력 조회(과거 시점 조회)에는 불필요하다고 확정(2026-09-24) — 이 3개는 제외하고 나머지 필드로 통일.**
- 9.2절 5단계(event 막대 클릭 시 뜨는 세션 목록 팝업)를 새로 만드는 시점에 `getSessions()` 기준 필드셋(위 3개 제외)으로 맞춤.
- `exec_count`(이력 조회 전용)는 유지할지, 아니면 4절에서 다룬 `sql_opcode` 기반 쿼리 타입 정보로 대체할지는 아직 미결정.
