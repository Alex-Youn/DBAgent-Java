## 구현 결과 (2026-09-21, 설계 대비 차이점)

구현하면서 설계 시점에는 몰랐던 것 두 가지가 나왔고, 둘 다 설계를 바꿔야 했다.

### (1) 설계에 없던 문제 — 재암호화해도 파일에 예전 B64 값이 남는다

암호화를 마친 뒤 DB 파일을 직접 열어보니 **예전 `B64(...)` 값이 그대로 검출**됐다(main SQLite: WAL에서
다수, AIX H2: 정상 종료 후에도 6건). B64는 키 없이 디코딩되므로, 이걸 안 지우면 "파일이 통째로 유출돼도
비밀번호는 안전하다"는 암호화의 목적 자체가 무너진다. 저장 엔진이 UPDATE 시 옛 페이지/청크 이미지를
파일에 남기기 때문이고, 설계문서 R3(백업 파일 유출)와는 별개의 **파일 내부 잔존(remanence)** 문제다.

대응이 엔진별로 갈렸다:

| | main (SQLite) | AIX (H2) |
|---|---|---|
| 방법 | 재암호화 직후 `PRAGMA wal_checkpoint(TRUNCATE)` + `VACUUM` | URL에 `DEFRAG_ALWAYS=TRUE` |
| 시점 | **기동 중 즉시** | JVM 정상 종료 시 |
| 실측 | B64 23건 → **0건** | 옵션 없이 종료 시 6건 잔존 → 옵션 켜면 0건 |

H2도 기동 중 즉시 처리하려고 `SHUTDOWN COMPACT`를 시도했으나, **DB가 닫혀버려 이어지는 질의가 전부
"Database is already closed"로 깨지고 앱이 아예 기동 실패**했다(실제로 겪음 - 다시 시도하지 말 것).
그래서 H2는 종료 시점 정리로 갔고, 그 한계를 코드 주석과 기동 WARN 로그에 명시했다.

> **AIX 운영 주의**: `stop-aix.sh`는 SIGTERM이라 JVM 셧다운 훅이 돌아 정리되지만, 개발기 Windows의
> `stop.ps1`은 `Stop-Process -Force`(강제 종료)라 훅이 안 돌아 잔재가 남는다. 즉 **폐쇄망에서는 업그레이드
> 후 한 번 정상 종료해야 예전 값이 지워진다** - 그 전에 `dbconfig.mv.db`를 외부로 복사하지 말 것.

### (2) 외부 override 파일에 URL 옵션을 같이 적어야 한다

`db_config/` 이전 때 이미 겪은 함정이 여기서도 나왔다 - jar 기본값의 URL에 옵션(`DEFRAG_ALWAYS`,
`busy_timeout`)을 붙여도, root/dist/dist-aix의 외부 `application.properties`가 **url을 통째로 덮어쓰면
옵션이 조용히 사라진다.** 그래서 AIX는 4곳(packaged + root/dist/dist-aix) 전부에 같이 적었다.

### 설계대로 간 부분 (검증 완료)

- 알고리즘/포맷: `AES/GCM/NoPadding`, 12B 랜덤 IV, 128b 태그, AAD=헤더, `ENC(v1:<keyId>:<base64>)` — 설계 그대로
- 키 관리: 환경별 독립 키, 최초 기동 시 자동 생성, 환경변수는 선택적 오버라이드, POSIX면 600 — 설계 그대로
- 마이그레이션: `db_config_meta`는 기록용, 판단은 매 기동 멱등 스캔 — 설계 그대로
- 추가로 넣은 것: `migrateFromJsonFile()`에서 **넣는 순간 암호화**(평문이 DB 파일에 한 번도 안 닿게)

### 실측 검증 결과 (main/AIX 공통)

| 항목 | 결과 |
|---|---|
| 키 자동 생성 | 256bit, 운영자 조작 0회 |
| 기존 B64 13건 재암호화 | 변경 13건 / 실패 0건 |
| 저장 형태 | `ENC(v1:k1:...)`, `accounts` JSON 안 추가 계정도 암호화됨 |
| 독립 복호화 검증 | 앱과 별개로 작성한 코드가 키 파일만으로 13건 전부 복호화, 평문 길이/첫 글자가 알려진 값과 일치 |
| 실제 DB 접속 | 복호화된 비밀번호로 도커 MySQL 접속 → 세션 목록 조회 성공(main/AIX 양쪽) |
| 재기동 멱등성 | 2회차 기동에서 재암호화 0건 |
| 관리 화면 CRUD | 신규 등록 시 암호화, **빈 비밀번호=기존 유지** 계약 유지, 삭제 정상 |
| 파일 잔재 | main 0건(즉시), AIX는 정상 종료 후 0건 |
| Java 8 호환 | AIX 빌드가 `--release 8`이라 Java 9+ API 사용은 컴파일 단계에서 차단됨(바이트코드 major 52 확인) |

**미확인 항목**: 폐쇄망 IBM J9의 `Cipher.getMaxAllowedKeyLength("AES")` 실측값(6-1 체크리스트) — 여기 개발기는
256이라 32바이트 키가 생성됐다. 폐쇄망이 128이면 코드가 자동으로 16바이트 키를 만들고 WARN을 남기므로
기동이 막히지는 않지만, 실제 값은 현장에서 확인 필요.

## 0. 조사 과정에서 나온 중요한 선행 사실 (설계의 전제)

### 0-1. 2026-08-18에 AES-256-GCM을 이미 한 번 구현했다가 롤백한 이력이 있음

`수정내역/커넥션풀_암호화_수정내역_2026-08-18.md` 56~64행에 명시되어 있다(원문 확인 완료):

> **1차 시도 (AES-256-GCM, 롤백됨)**: 키를 OS 환경변수(`DBAGENT_ENC_KEY`)로만 관리하는 진짜 암호화 방식으로 구현 → 실제 Oracle 19c로 접속까지 검증 성공. 하지만 **키 생성 / 서버별 환경변수 등록 / 키 분실 시 복구 불가** 등 운영 부담이 크다는 사용자 피드백을 받아 (...) AES 관련 코드(`PasswordCipher` 클래스, `DbAgentApplication`의 `--enc-tool` 분기)는 전부 삭제

즉 이번 6단계는 "기술적으로 되는가"의 문제가 아니라 **"그때 롤백 사유였던 운영 부담 3가지를 이번 설계가 실제로 해소하는가"**의 문제다.

| 2026-08 롤백 사유 | 2026-09 현재 상황 | 이번 설계의 대응 |
|---|---|---|
| 키 생성 부담(CLI `--enc-tool` 실행 필요) | — | **최초 기동 시 키 파일 자동 생성**. 운영자 조작 0회 |
| 서버별 환경변수 등록 부담 | — | **환경변수 필수 아님**. jar 옆 키 파일이 기본, 환경변수는 선택적 오버라이드 |
| 키 분실 시 복구 불가 | 4-1에서 관리 화면(`db-mgmt.html`) CRUD 완비, `databases.json` 손편집 경로 소멸 | 키 분실 = **관리 화면에서 비밀번호 재입력**(인스턴스 11~13개). 치명적 사고가 아니라 반나절 복구 작업으로 격하됨 |
| (당시) 비밀번호를 사람이 파일에 손으로 넣어야 해서 CLI 인코딩 도구가 필수 | 입력 경로가 관리 화면 하나로 단일화됨 | **CLI 암호화 도구 자체가 불필요** → `b64-tool.ps1`의 AES 버전을 만들 이유가 없음(후술) |

> 결론: 2026-08 롤백의 원인은 "AES가 과했다"가 아니라 **"키 배포와 비밀번호 입력을 사람 손으로 하게 만든 설계"**였다. 4-1/5단계로 입력 경로가 UI로 통일된 지금은 같은 부담이 재현되지 않는다. 나중에 "예전에 접었던 거 아닌가"라는 질문이 나올 수 있으니 이 문서에 근거를 남겨둔다.

### 0-2. 비밀번호 저장 지점 전수 조사 결과 (2026-09-21 기준)

| 위치 | 현재 형식 | 이번 범위 |
|---|---|---|

- 코드상 `password` 문자열을 **동등 비교(equals)하는 지점은 없음** — `validateAccounts()`는 blank 여부만 보고, `findExistingAccountPassword()`는 저장값을 그대로 복사한다. 따라서 "같은 평문이 매번 다른 암호문이 되는" 랜덤 IV 방식을 써도 기존 로직이 깨지지 않는다(반드시 확인해야 했던 전제, 통과).

## 1. 암호화 알고리즘 — 대안 비교와 권고

### 옵션 A. 표준 `javax.crypto` 직접 사용 — AES/GCM/NoPadding (★ 권고)

- **핵심**: 자체 `CredentialCipher` 클래스 1개. `Cipher.getInstance("AES/GCM/NoPadding")`, 암호화마다 12바이트 난수 IV, 128비트 인증 태그.
- **장점**: 의존성 0개 추가, Java 8/17 표준 API로 main/AIX 완전 동일 코드 작성 가능, 저장 포맷을 우리가 100% 통제(버전/키ID 헤더로 롤백·로테이션 대응), AEAD라 변조 시 `AEADBadTagException`으로 실패(CBC 대비 우위), 신규 서드파티 jar 0개(폐쇄망 반입 심사 부담 없음).
- **단점/리스크**: 암호 코드를 직접 짜므로 IV 재사용 금지 같은 실수 여지(완화: SecureRandom 매번 생성 강제, 리뷰 체크 항목화), IBM J9 Java 8에서 AES-256은 무제한 정책 파일이 필요할 수 있음(1-2절에서 대응).

### 옵션 B. Spring Security Crypto `Encryptors.stronger(password, salt)`

- **장점**: 암호 코드를 한 줄도 안 씀, 의존성 이미 있음(내부적으로 AES-256-GCM).
- **단점**: 키가 아니라 패스프레이즈 기반(PBKDF2 반복 1024 고정) — 키 관리 문제가 사라지는 게 아니라 이름만 바뀜. 저장 포맷이 라이브러리 내부 규약이라 **버전/키ID 헤더를 넣을 수 없어** 키 로테이션·혼재 상태·롤백 판별을 다룰 수 없음(이번 요구사항과 정면 충돌). main(Spring Security 6)과 AIX(5.7) 버전 차이로 포맷 리스크도 존재 — dual-project-sync와 궁합 나쁨.

### 옵션 C. JCEKS/PKCS12 키스토어 + 키스토어 비밀번호는 환경변수

- **장점**: 키 파일 자체가 암호화됨.
- **단점**: 부트스트랩 문제가 한 겹 내려갈 뿐(키스토어 비밀번호를 또 어딘가에 둬야 함), 운영 절차가 늘어나 **2026-08 롤백 사유(운영 부담) 재현 위험이 가장 큼**, IBM J9의 JCEKS SecretKeyEntry 지원은 버전별 편차가 있어 별도 실검증 필요.

### 옵션 D. OS 자격증명 저장소(Windows DPAPI 등)

- **탈락.** AIX에 DPAPI 동급 기능이 없어 main/AIX 동일 코드가 원천적으로 불가능(dual-project-sync 위반). 머신 바인딩이라 서버 이관 시 복호화 불가.

### ★ 최종 권고: 옵션 A — AES-256-GCM(키 길이 가변), 12바이트 랜덤 IV, 128비트 태그, AAD = 헤더 문자열

| 항목 | 값 | 근거 |
|---|---|---|
| 알고리즘 | `AES/GCM/NoPadding` | AEAD, Java 8/17 표준, IBM J9 Java 8 지원 확인됨 |
| 키 길이 | 키 파일에 든 길이를 그대로 사용(16/24/32B, 신규 생성 시 32B 우선·불가 시 16B) | 1-2절 참조 |
| IV/nonce | 암호화 1회마다 `SecureRandom` 12바이트 신규 생성, 상수/카운터 IV 금지 | GCM에서 IV 재사용은 즉시 키 복구로 이어지는 치명적 오용 |
| 인증 태그 | 128비트 | 표준 최대 |
| AAD | 헤더 문자열 `"v1:<keyId>"`의 UTF-8 바이트 | 버전/키ID 필드 변조를 태그로 함께 검출, 비용 0 |
| Cipher 인스턴스 | 호출마다 `Cipher.getInstance`(thread-safe 아님), `SecureRandom`은 static 1개 공유 | `resolve()`가 고빈도 경로지만 인스턴스 13개·수십 µs 수준이라 무시 가능 |

**AAD에 db_id는 v1에서 넣지 않는다.** 행 복사 공격은 막아주지만, `dbconfig.db` 쓰기 권한이 있는 공격자는 원래 행의 host만 자기 서버로 바꿔도 앱이 복호화한 평문을 탈취할 수 있어 실효 방어가 아니다. 오히려 db_id 변경·DB 파일 이관 시 "원인 불명 복호화 실패"만 늘린다 → **진짜 방어선은 파일 쓰기 권한 통제**라는 점을 잔여 위험(R12)으로 명시한다.

### 1-2. AIX(IBM J9 Java 8) 실무 주의 — 이 설계에서 가장 실패 확률 높은 지점

`설계문서/AIX-DEPLOYMENT-REVIEW.md` 152~157행 기준, 폐쇄망 서버 Java는 **IBM J9 Java 8(1.8.0_251, SR6 FP10)**.

1. **AES-256 = 무제한 정책 파일 필요 가능성.** 폐쇄망이라 "필요하면 그때 받아서 깔지"가 안 됨.
   - **완화(핵심 결정)**: 키 자동 생성 시 `Cipher.getMaxAllowedKeyLength("AES")`를 조회해 `>= 256`이면 32바이트, 아니면 **16바이트(AES-128-GCM)로 생성 + WARN 로그**. AES-128-GCM도 실무상 충분한 강도 — 정책 파일 때문에 기동이 막히는 일이 없게 한다. main/AIX 코드는 동일, 키 파일 내용만 환경별로 다름.
   - 32바이트 키를 쓰는 환경에서 max < 256이면 기동 시 명확한 에러로 fail-fast(정책 파일 설치 또는 128비트 키 재생성 안내).
2. AES/GCM 자체는 IBM Java 8 지원됨. 단 구버전 `IBMJCEPlus`의 `Cipher.update` 스트리밍 제약 이력 있음 → **우리는 `doFinal()` 원샷만 사용**하므로 해당 없음.
3. **`SecureRandom` 엔트로피 지연** — AIX 최초 키 생성 시 `/dev/random` 블로킹으로 기동이 멈추는 사례 있음 → 증상 발생 시 `-Djava.security.egd=file:/dev/urandom` 추가를 가이드에 명시.
4. **컬럼 길이(AIX H2 전용)**: `db_instances.accounts VARCHAR(4000)`. 암호문은 계정당 약 +50자 늘어남(IV/태그 28B → base64 +38자, 헤더 11자) → **`VARCHAR(8000)`으로 확대** 권고. `password VARCHAR(500)`은 변경 불필요. main(SQLite TEXT)은 변경 불필요.

**착수 전 확인 필수**: 폐쇄망 IBM Java 8에서 `Cipher.getMaxAllowedKeyLength("AES")` 실측값(256/128)을 6-1 단계에서 먼저 확보한다.

## 2. 암호문 저장 포맷

### 2-1. 최종 포맷

```
ENC(v1:k1:<base64(IV 12B ‖ ciphertext ‖ tag 16B)>)
```

- `ENC(` … `)`: 기존 `B64(...)` 관례를 계승한 래퍼 — 눈으로도 코드로도 즉시 구분.
- `v1`: 포맷/알고리즘 스위트 버전(AES-GCM + 12B IV + 128b tag + AAD=헤더). 파라미터가 바뀌면 `v2`.
- `k1`: 키 ID(`[A-Za-z0-9_-]{1,16}`) — 로테이션의 핵심, 구키/신키 암호문이 한 테이블에 공존해도 어느 키로 풀지 알 수 있다.
- base64: 표준 알파벳, 줄바꿈 없음. JSON/SQL 바인딩에 안전.

### 2-2. 판별 규칙(`decrypt(raw)`)

| 입력 | 처리 |
|---|---|
| `null`/빈 문자열 | 그대로 반환(빈 비밀번호는 암호화 안 함 — `updateInstance`의 "blank면 기존 유지" 계약과 충돌 방지) |
| `ENC(` … `)` | 파싱 → 버전/키ID 확인 → 복호화. 미지의 버전/키ID는 **명시적 예외**(조용한 평문 통과 금지) |
| `B64(` … `)` | 레거시 경로. base64 디코드해서 평문 반환(마이그레이션 유예용, 2~3릴리즈 후 제거 검토) |
| 그 외 | 레거시 평문 그대로 통과(현재 `resolvePassword()`와 동일 동작) |

`encrypt()`는 항상 `ENC(v1:<active key id>:...)`만 생산한다.

### 2-3. 왜 "별도 컬럼 추가"가 아니라 래퍼 문자열인가

- 비밀번호는 `password` 컬럼뿐 아니라 `accounts` JSON 배열 안에도 있다 — 컬럼 방식은 JSON 안쪽에 적용 불가, 두 저장 지점이 서로 다른 메커니즘을 갖게 됨(유지보수 최악).
- SQLite/H2 두 방언에 스키마 변경 비용이 안 듦(accounts 폭 확대 1건 외 스키마 변경 0).
- 자기 기술(self-describing) 포맷이라 혼재 상태(B64 + ENC + 평문 동시 존재)가 정상 동작 — 마이그레이션 중단·부분 실패·롤백 상황에서 결정적.
- `resolvePassword()`/`encodePassword()` 호출부(4곳)를 하나도 안 건드려도 된다(메서드 시그니처 동일 유지).

→ **기존 `B64(...)` 래퍼 패턴을 유지·확장하는 것이 맞다.**

## 3. 키 관리 — 멀티 환경(개발 PC / 사내망 PC / 폐쇄망 AIX) 반영

### 3-1. 키 소스 우선순위(모두 선택, 운영자는 아무것도 안 해도 됨)

1. 환경변수 `DBAGENT_MASTER_KEY`(형식: `k1:<base64키>` 또는 키 파일 전체 내용) — 선택적 오버라이드
2. 프로퍼티 `dbagent.security.key-file=<경로>` — 경로 지정
3. 기본값: 작업 디렉터리의 `dbagent.key` — 없으면 자동 생성

> 2026-08 롤백의 직접 원인이 "서버마다 환경변수를 등록해야 함"이었으므로, **환경변수를 필수로 만들지 않는 것**이 이번 설계의 핵심 결정이다.

### 3-2. 키 파일 포맷(`java.util.Properties`, Java 8/17 동일)

```properties
# DBAgent credential master key
# 이 파일이 유출되면 등록된 모든 대상 DB 비밀번호가 복호화됩니다.
# git 커밋 금지 / backup_* 폴더에 복사 금지 / dbconfig.db와 같은 매체에 백업 금지
active=k1
key.k1=<base64 32B or 16B>
created.k1=2026-09-22
```

- 여러 `key.<id>` 공존 가능 → 로테이션 시 구키를 남긴 채 신키로 재암호화 가능.
- 생성 시 POSIX 환경이면 `Files.setPosixFilePermissions`로 `600` 적용(Windows는 POSIX 뷰가 없으므로 `supportedFileAttributeViews().contains("posix")` 가드 필수 — 없으면 WARN만).
- 키 값은 어떤 경우에도 로그에 찍지 않음(로드 성공 시 active key id와 키 길이만 INFO).

### 3-3. 환경마다 같은 키 vs 다른 키 — 핵심 결정 (★ 확정: K2, 2026-09-21 오케스트레이터 결정)

| | K1. 전 환경 공용 키 1개 | K2. 환경별 독립 키(★ 권고) |
|---|---|---|
| 키 이동 | 개발 PC→사내망→폐쇄망으로 **반입** 필요(USB/반입심사) | 이동 없음 — 각 환경이 최초 기동 시 스스로 생성 |
| `dbconfig.db` 환경 간 복사 | 가능(암호문 그대로 이동) | 불가(복호화 실패) |
| 유출 파급 | 개발 PC 1대 털리면 폐쇄망 운영 DB 비밀번호까지 전부 노출 | 해당 환경으로 한정 |
| 기존 관례와의 정합 | 어긋남 | `application.properties`/`databases.json`을 환경별로 따로 두고 git에서 빼는 기존 원칙과 동일 |
| 운영 부담 | 키 반입 절차 + 분실 시 전 환경 영향 | 0(자동 생성) |

**권고: K2(환경별 독립 키).** "회사에서 만든 암호화 값을 폐쇄망으로 그대로 옮길 수 있는가?"의 답은 K2에서는 "옮길 수 없고, 옮기지 않는 것이 의도"다. 비용은 사실상 0 — 4-1 폐쇄망 적용 실적(체크리스트 125~135행)에서 이미 "폐쇄망에는 인스턴스 2개만 이관하고 나머지는 관리 화면에서 직접 등록"하는 방식이 정상 경로로 확정된 상태라, 지금도 `dbconfig.db`를 환경 간에 복사하지 않는다.

- 환경 간 이관이 필요한 유일한 경우는 "평문 `databases.json`으로 1회 자동 마이그레이션"인데, 이 경로는 **암호화 도입 후에도 그대로 동작**한다(평문 입력 → 저장 시 자동 암호화).
- 향후 "환경 간 DB파일 복사"가 필요해지면 그때 K1으로 전환 가능(키 파일 하나만 복사). keyId 덕분에 K2→K1 전환도 무중단.

### 3-4. 키 파일을 어디에 둘 것인가

솔직한 위협 모델: **키 파일과 `dbconfig.db`가 같은 폴더에 있으면, 서버를 장악한 공격자에게는 평문과 다를 바 없다.** 이 암호화가 실제로 막는 것은:
- `dbconfig.db`만 따로 복사·전달되는 경우(장애 분석용 공유, 백업 매체, 실수로 git 커밋, `.bak` 유실)
- 현재 저장소에 `backup_2026-09-02/`, `backup_pull_*/`, `dist/*.bak-*`, `databases.json.bak-*`가 잔뜩 쌓여 있는 관행 — **지금 가장 현실적인 유출 벡터**

→ **권고: 키 파일은 앱 디렉터리(`dist/`) 바깥, 백업 스크립트 범위 밖에.**
- Windows 예: `C:\ProgramData\DBAgent\dbagent.key`(`dbagent.security.key-file`로 지정)
- AIX 예: `~dbagent/.dbagent/dbagent.key`(퍼미션 600)
- 기본값(작업 디렉터리 `dbagent.key`)은 "설정 안 해도 돌아가게" 하기 위한 fallback이며, 운영 환경에서는 경로를 명시적으로 지정하는 것을 표준 절차로 문서화.

### 3-5. 키 로테이션 정책

**구분**: "마스터 키 로테이션"(앱이 비밀번호를 감싸는 키 교체)과 "대상 DB 비밀번호 로테이션"(DBA가 Oracle 계정 암호를 바꾸는 것)은 완전히 다른 작업이다. 마스터 키를 바꿔도 DB 비밀번호는 그대로, 그 반대도 마찬가지.

| 트리거 | 조치 |
|---|---|
| 키 유출 의심(파일 유출, 백업 매체 분실, git 실수 커밋) | 즉시 로테이션 + 대상 DB 비밀번호도 함께 변경(키만 바꿔도 이미 유출된 평문은 유효) |
| 담당자 퇴사/인수인계 | 키 로테이션 |
| 정기 | 연 1회 권고(강제 아님) — 인스턴스 10여 개 규모에서 분기 로테이션은 과잉 |
| 알고리즘 상향(AES-128→256, 정책 파일 설치 후) | 새 keyId로 로테이션하면 자연 전환 |

**로테이션 절차(재기동 1회 필요 — jar 교체와 같은 창 사용)**
1. 키 파일 백업(구키 보존 필수)
2. 키 파일에 `key.k2=<신규 base64>` 추가, `active=k2`로 변경. **`key.k1`은 지우지 않는다.**
3. 앱 재기동 → 기동 시 재암호화 루틴(5절)이 `keyId != active`인 모든 행을 구키로 복호화 → 신키로 재암호화
4. 로그에서 `재암호화 N건 완료, 실패 0건` 확인 + 각 DB 엔진 접속 1건씩 스모크 테스트
5. 확인 후 `key.k1` 줄 삭제 → 재기동(선택)

### 3-6. 키 분실 대비(2026-08 롤백 사유의 정면 대응)

- 키 파일은 `dbconfig.db`와 다른 장소에 별도 보관(사내 비밀번호 관리 대장, 폐쇄망이면 운영 문서 캐비닛). 같은 백업 매체에 넣으면 암호화 의미 소멸.
- 키를 잃어도 복구 경로 명확: 관리 화면에서 각 인스턴스 비밀번호만 재입력(11~13건). **"복구 불가"가 아니라 "반나절 수작업"**.
- 복호화 실패 행은 기동을 막지 않고(5-2) ERROR 로그로 인스턴스 ID만 알려주므로, 어느 걸 다시 넣어야 하는지 바로 드러난다.

## 5. 마이그레이션 절차 (B64/평문 → AES)

### 5-1. 트리거 방식 — "1회성 플래그"가 아니라 "멱등 스캔"을 권고

`db_config_meta` 테이블은 재사용하되 **"플래그로 1회만 실행" 의미론은 쓰지 않는다.**

- 대상 행이 10여 개 — 매 기동 전수 스캔해도 비용 사실상 0(수 ms).
- 플래그 방식은 자기치유(self-healing)가 안 됨 — 롤백으로 구 jar를 잠깐 돌려 행 하나가 `B64(...)`로 덮어써지거나, 키 로테이션으로 keyId가 바뀌거나, 마이그레이션이 일부 행에서 실패하면 플래그가 이미 1일 때 영원히 다시 안 돈다.
- 스캔 방식이면 최초 마이그레이션과 로테이션 재암호화가 같은 코드 한 벌로 끝난다(별도 로테이션 로직 불필요).

```
reencryptAllPasswords():   // init()에서 매 기동 호출, writeLock 안에서
  rows = SELECT id, password, accounts FROM db_instances
  for row in rows:
     try:
        newPw  = needsReencrypt(row.password) ? encrypt(decrypt(row.password)) : row.password
        newAcc = accounts JSON의 각 원소 password에 동일 적용(없으면 null 유지)
        if 변경 있음: UPDATE db_instances SET password=?, accounts=? WHERE id=?   // 행 단위 개별 커밋
        changed++
     catch (복호화 실패 등):
        failed++; log.error("인스턴스 '{}'의 비밀번호를 현재 키로 복호화할 수 없습니다 - 관리 화면에서 재입력이 필요합니다", id)
        // 원본 행은 손대지 않음
  UPDATE db_config_meta SET password_key_id=activeKeyId, password_format_ver=1, reencrypted_at=now()
  log.info("비밀번호 재암호화: 변경 {}건, 실패 {}건 (활성 키 {})", changed, failed, activeKeyId)
```

`needsReencrypt(stored)` = `stored`가 빈 값이 아니고 (`ENC(` 래퍼가 아니거나 / 버전이 `v1`이 아니거나 / keyId가 active가 아닌) 경우 true.

### 5-2. 실패 시 처리 원칙

- **기동을 막지 않는다.** `warnOnDuplicates()`/`errorOnMissingOracleHost()`가 세운 기존 원칙(한 인스턴스의 문제로 전체를 못 쓰게 만들지 않음)을 그대로 따른다.
- 실패 행은 원본 그대로 보존(부분 암호화·손상 상태를 만들지 않음). 해당 인스턴스만 접속 실패, 나머지는 정상.
- 로그에는 인스턴스 ID만 — 암호문·평문·키는 절대 출력 금지.
- 단, **키 파일 자체를 못 읽거나 키 길이가 정책에 안 맞는 경우는 fail-fast(기동 중단)**. 전체 영향이라 조용히 넘기면 모든 인스턴스가 이유 없이 죽는 것처럼 보인다.

### 5-3. 롤백 시나리오(반드시 문서에 명시)

- 신 jar로 재암호화가 끝난 `dbconfig.db`를 구 jar로 되돌리면, 구 jar의 `resolvePassword()`는 `ENC(...)`를 "평문"으로 간주해 그 문자열 그대로 DB에 접속 시도 → **인증 실패**(엉뚱한 DB 접속 같은 위험한 실패가 아니라 명확한 인증 실패인 것은 다행).
- 따라서 **배포 전 `dbconfig.db`/`dbconfig.mv.db` 백업은 선택이 아니라 필수 절차.** 롤백 = 구 jar + 백업 DB 파일 복원 세트.
- 검토 후 기각한 대안: `password_enc` 컬럼 추가로 구/신 값 동시 유지(dual-write) → 구 jar도 계속 동작. 기각 사유: 행 10여 개짜리 작업에 스키마 복잡도만 더하고, 평문/B64 값이 그대로 남아 암호화 목적 자체가 무효화됨.

### 5-4. 폐쇄망 적용 절차(4-1의 성공 패턴 재사용)

1. 폐쇄망 서버에서 `dbconfig.mv.db` 백업(기존 `backup_*` 관행대로, 단 키 파일은 여기 넣지 않음)
2. 신 jar 교체 → 최초 기동 → 키 파일 자동 생성(운영자 조작 없음) → 재암호화 자동 수행
3. 로그에서 `활성 키 k1`, `재암호화 N건, 실패 0건` 확인
4. 생성된 키 파일을 앱 디렉터리 밖 지정 경로로 이동(`dbagent.security.key-file` 지정) + 퍼미션 600 확인 + 별도 장소에 사본 1부 보관
5. 인스턴스별 접속 스모크 테스트
6. 남아 있는 `oracle.env`/`databases.json` 실서버 파일 삭제(4~5단계의 미완 항목과 동시 처리 가능)

## 8. 최종 권고 요약 (4가지 결정 사항)

1. **알고리즘**: 표준 `javax.crypto`의 **AES-GCM**(키 길이는 환경이 허용하는 최대: 256 우선, IBM J9 정책 제약 시 128 자동 폴백). 외부 라이브러리 0개 — 체크리스트 원문의 "AES-256"은 **"AES-GCM, 키 길이는 가변"**으로 완화해 적는다.
2. **저장 포맷**: `ENC(v1:<keyId>:<base64(IV‖CT‖TAG)>)` — 기존 `B64(...)` 래퍼 패턴 계승, 별도 컬럼 추가 없음. `accounts` JSON 내부까지 동일 규칙으로 커버되고 혼재/롤백 상태를 자연스럽게 다룰 수 있는 것이 결정적 이유.
3. **키 관리**: **환경별 독립 키**(K2, 확정)를 **앱 디렉터리 밖 키 파일**에, **최초 기동 시 자동 생성**. 환경변수는 필수가 아닌 선택적 오버라이드. 로테이션은 keyId 다중 보유 + 기동 시 자동 재암호화, 정기 주기는 연 1회(권고 수준).
4. **마이그레이션**: `db_config_meta` 테이블은 기록용으로만 재사용하고, 실제 판단은 매 기동 멱등 스캔. 실패 행은 보존+ERROR 로그, 기동은 계속(기존 `warnOnDuplicates()` 원칙 승계).

**3번(환경별 키 vs 공용 키) 확정: K2(환경별 독립 키)로 2026-09-21 결정 완료.** 실무적 의미: `databases.json` 경유 초기화/수동 등록 절차는 전혀 안 바뀌고, `dbconfig.db` 파일 자체를 다른 서버로 복사하는 방식만 쓸 수 없게 된다(키가 없어 복호화 실패 → 해당 인스턴스만 관리 화면 재입력 필요). 이 프로젝트는 지금도 DB 파일을 환경 간에 복사하지 않으므로 실질 영향 없음.

> **진행 상태(2026-09-21)**: 설계 확정, **코드 변경은 아직 하지 않음** — 사용자 지시로 구현 착수 보류 중. 단, `security-poc/`에 이 설계를 검증하는 독립 프로토타입(DBAgent-Java 실제 소스는 미변경)을 만들어 8개 시나리오 15개 체크 전부 통과 확인함(README.md 참고).

**프로토타입 실행 중 발견해 설계보다 더 정확해진 디테일**: "다른 서버로 `dbconfig.db`만 복사해온 경우"(3-3절 시나리오) 실패 원인은 당초 예상한 "keyId를 못 찾음"(`IllegalArgumentException`)이 아니라, 두 서버가 키 자동 생성 시 기본 keyId를 똑같이 `k1`로 쓰기 때문에 "keyId는 있는데 값이 달라 인증 태그 불일치"(`AEADBadTagException`)로 실패하는 경우가 실무에서 더 흔하다. **결과(복호화 실패, 기동은 안 막힘)는 설계 의도와 동일**하므로 설계 자체는 변경 없음 — 실제 구현 시 로그 문구/예외 처리에서 이 두 경우(키 없음 / 키 값 불일치)를 구분하지 말고 "복호화 실패"로 동일하게 처리하면 된다는 점만 확인.
