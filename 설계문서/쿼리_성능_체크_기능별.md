# 쿼리 성능 체크(기능별) — 폐쇄망 측정 가이드

작성 기준: 2026-09-26 시점 `src/main/java/com/dbagent/` 소스(main 프로젝트).
AIX 이관본은 동일 SQL을 그대로 실행하므로
이 문서를 함께 쓴다. 대상 Oracle 11g~21c(RAC 가능), 앱 서버 AIX. 폐쇄망은 접속·조회가 제한적이므로, 이 문서는
"이 기능이 왜 무거울 수 있는지"와 "폐쇄망에서 안전하게 실측하는 SQL"을 짝지어 정리한다.

**주의(라이선스)**: 이 앱의 상당수 화면·수집기가 `v$active_session_history`(ASH)와
`dba_hist_active_sess_history`/`dba_hist_snapshot`(AWR)을 직접 SELECT한다. 이 두 뷰는 **Oracle Diagnostics Pack**
라이선스 대상이다. 폐쇄망 DB에 Diagnostics Pack 라이선스가 없다면 해당 화면(Active Session Wait Class 차트, Top SQL,
성능 이력 조회, 성능 분석, 대시보드 개편 Top/드로어 등)은 애초에 켜면 안 되는 기능이라는 점을 먼저 확인해야 한다.
`SELECT * FROM v$active_session_history WHERE ROWNUM = 1` 한 줄로 접근 권한/에러(ORA-)를 먼저 확인해라.

이 문서는 기능마다 다음을 적는다: 화면/메뉴 → 호출 API/수집기 → 실행 주기 → 조회 대상 뷰 → 주의점 → 제한시간(타임아웃
프로퍼티+기본값) → 예상 부하 등급(낮음/중간/높음). 실측 SQL·판정 기준은 3장에 모았다.

## 1. 우선 측정 순서 (Top 7)

폐쇄망 실측 시간이 제한적이라면 아래 순서로 본다. 근거는 코드 실측(주석에 남은 실측치)과 "주기 × 대상 인스턴스 수"로
계산한 상대적 부하다.

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | **성능 이력 조회**(`/api/history_sessions`, `/api/history_top_sessions`) | `dba_hist_active_sess_history`를 **snap_id 파티션 프루닝 없이 sample_time만으로** 스캔한다(2.4절). 사용자가 조회 구간을 넓게 잡으면(예: 최근 7일) AWR 보관 기간 전체를 다 훑을 수 있다 - 이 앱에서 가장 폭주 위험이 큰 단일 쿼리다. |
| 2 | **v$lock 스캔이 들어간 모든 쿼리**(TM Lock 탭, Lock Holder/Waiter Tree, active_alerts의 Blocking 판정, failure_prob, 대시보드 Lock 실시간) | 코드 주석에 실측치가 남아 있다: "이 환경 일부 인스턴스에서 v$lock 스캔 자체가 **49초**까지 걸릴 수 있음(enqueue 해시체인이 김)". 이미 3초 타임아웃으로 캡을 걸어놨지만, 폐쇄망 실제 인스턴스에서 이 스캔이 몇 초 걸리는지가 다른 화면(같은 커넥션 풀을 쓰는)까지 영향을 준다. |
| 3 | **fleet_status 폴링**(`/api/fleet_status`) | `dbagent.fleet-overview.polling-interval-ms`(기본 **3초**)마다 설정된 **모든 DB 인스턴스**에 대해 병렬로 `v$instance`/`v$sysmetric`/`v$osstat`/`v$sgastat`/`v$pgastat`/`v$sysmetric`(트랜잭션) 등 6~7개 쿼리를 돌린다. Fleet Overview 화면을 열어 둔 사람 수만큼 배가되지는 않지만(인플라이트 중복 제거 없음 - fleet_status는 요청마다 새로 조회), 등록된 DB 수가 많은 폐쇄망(문서에 "11개 DB" 사례 언급)에서는 3초마다 전체 인스턴스에 부하가 걸린다. |
| 4 | **Current Session 화면 폴링**(`/api/session`, `/api/session_extra`) | `dbagent.ui.polling-interval-ms`(기본 **2초**)로 갱신된다(app.js 주석). `getSessions()`/`queryActiveTransactions()`는 매 호출마다 `v$active_session_history WHERE sample_time >= SYSDATE - 1/24/60`(최근 1분) 인메모리 집계 + `v$session`/`v$process`/`v$sql` 조인을 한다. 인메모리 스캔이라 개별 호출은 가볍지만, 2초 주기 × 열린 탭 수로 누적된다. |
| 5 | **60초 백그라운드 샘플러**(`InstanceMetricSamplerService`) | 화면을 아무도 보고 있지 않아도 **등록된 모든 Oracle 인스턴스**에서 60초마다 자동 실행된다. ASH 스캔(7분류+8분류+성능분석 수집까지 한 번에), v$lock, 테이블스페이스 사용률(`dba_data_files`/`dba_free_space` 조인)을 포함한다. 인스턴스 등록 직후·앱 기동 직후에는 최근 60분을 채우는 **백업(backfill)** 쿼리도 함께 도는데, 이건 타임아웃이 60초로 더 길게 잡혀 있다(4.2절). |
| 6 | **일 단위 점검**(`CheckCollector.checkDaily`, 새벽 3시 + 기동 직후) | `dba_segments` 전체 스캔(테이블 용량) + `dba_objects WHERE status='INVALID'` 전체 스캔을 **등록된 모든 DB**에 대해 돌린다. 딕셔너리 뷰 풀스캔이라 스키마/세그먼트 수가 많은 운영 DB에서 시간이 걸릴 수 있다(타임아웃 기본 120초, 커넥션 read-timeout 60초에 맞춰 자동으로 줄어듦 - 4.2절 `dailyTimeout()` 참고). |
| 7 | **v$sqlstats 60초 델타 수집**(`SqlStatDeltaCollector`) | `SELECT ... FROM v$sqlstats WHERE last_active_time >= SYSDATE - 2/1440` - last_active_time에 인덱스가 없어 **X$ 고정 테이블 전체 스캔**이 구조적으로 불가피하다(코드 주석: "시간 조건으로는 어느 뷰도 인덱스 접근 불가"). 공유 풀(shared pool)에 캐시된 SQL 커서 수가 많은 운영 DB일수록 이 스캔이 오래 걸린다. |

이 외 항목은 2장 표에서 부하 등급 "중간" 이상만 추려서 다음으로 본다.

## 2. 기능별 점검표

컬럼: **기능(화면/메뉴)** · **API/수집기** · **실행 주기·트리거** · **조회 대상 뷰/테이블** · **핵심 조건·주의점** ·
**제한시간(프로퍼티, 기본값)** · **예상 부하 등급(사유)**.

### 2.1 Current Session (세션 모니터링)

| 기능 | API/클래스 | 주기 | 대상 뷰 | 주의점 | 제한시간 | 부하 |
|---|---|---|---|---|---|---|

| Parallel Session 탭 | `queryParallelSessions()` | session_extra와 동일 | `v$px_session` JOIN `v$session` | 가벼움(병렬 세션 자체가 드묾) | 없음 | 낮음 |
| DB Link 세션 탭 | `queryRemoteSessions()` | session_extra와 동일 | `v$session`(program/event 패턴 매칭) | LIKE 패턴 매칭이지만 v$session 자체가 작아 무시할 수준 | 없음 | 낮음 |
| 2PC Pending 탭 | `queryPending2pc()` | session_extra와 동일 | `dba_2pc_pending` | 대부분 계정에 권한 없음 - 실패해도 조용히 빈 탭(설계상 정상) | 없음 | 낮음 |
| Session Wait(Lock) 카운트 | `queryLockWaitSidsByType()` (session_extra 안에 포함) | session_extra와 동일 | `v$lock WHERE request > 0` | **1번 우선순위 참고**: v$lock 스캔 49초 실측 사례 있음. 타임아웃 걸려 있어 실패 시 빈 리스트로 폴백(락 목록을 "일부만" 보여주지 않도록 전부 비움) | `dbagent.monitor.lock-query-timeout-seconds`(기본 3초) | 중간~높음(인스턴스별 편차 큼) |

| 세션 상세(SQL/실행계획) | `GET /api/session_query` → `getSessionQuery()` | 클릭 시 1회 | `v$session`, `v$active_session_history`(세션 종료 시 폴백), `v$sql`, `DBMS_XPLAN.DISPLAY_CURSOR`, `v$sql_bind_capture` | `DISPLAY_CURSOR`는 커서가 라이브러리 캐시에서 밀려났으면 빈 결과 - 정상. 실행계획 조회 자체가 비용 큰 작업은 아님 | 없음 | 낮음(단발성) |
| Kill Session | `POST /api/kill_session` → `killSessions()` | 사용자 액션 | `v$session`(재조회) + `ALTER SYSTEM KILL SESSION` | ALTER SYSTEM은 바인드 변수를 못 써서 정수 검증이 유일한 방어선(코드 주석) - 성능 이슈는 아니고 안전성 이슈 | 없음 | 낮음(단발성) |

| 테이블 구조 조회(SQL 작성기) | `TableInfoService.fetchTableInfo()` | 사용자 액션 | `user_tab_columns`/`all_tab_columns`, `user_ind_columns`/`all_ind_columns` | OWNER 탐색이 필요하면 `all_tab_columns WHERE table_name=?` 조회가 한 번 더 붙음(테이블명 인덱스라 가벼움) | 없음 | 낮음 |
| SQL 정합성/튜닝(sLLM), SQL Tune Advisor(RAG) | `SqlTuningService`, `SqlTuneAdvisorService` | 사용자 액션 | **Oracle 아님** - 외부 HTTP(FastAPI/RAG 서버) 호출뿐 | 이 기능 자체는 Oracle 부하가 없다. 다만 프롬프트에 실행계획/SQL 텍스트를 넣기 위해 위 실행계획 조회 기능을 먼저 쓰는 흐름이라, 그 앞단(EXPLAIN/실제 실행)의 부하만 고려하면 됨 | (HTTP 타임아웃 별도, `sqltuning.api.timeout-ms` 등) | 해당없음(Oracle 기준) |

### 2.9 RDB(MySQL/MariaDB/Postgres/MSSQL/CUBRID) — 참고용, Oracle 아님

이 앱은 Oracle 외 4개 엔진도 같은 구조(세션 목록/락/대기 이벤트/용량/fleet_status)로 모니터링한다.
`MySqlMonitorService`/`PostgresMonitorService`/`MsSqlMonitorService`/`CubridMonitorService`가 각각
`information_schema.PROCESSLIST` 계열, `pg_stat_activity`/`pg_database`, `sys.dm_exec_*`/`sys.dm_os_*` DMV,
`SHOW TRANSACTION TABLES`/`SHOW THREADS`(CUBRID 고유 명령)를 쓴다. 이 문서는 Oracle이 우선순위이므로 상세 표는
생략하되, 같은 **fleet_status 폴링 주기(3초)**가 이 엔진들에도 동일하게 적용된다는 점만 유의해라(2.3절 Fleet
Overview 항목과 동일한 위험). MSSQL 쪽 `sys.dm_db_partition_stats` 기반 테이블 용량 조회는 동적 SQL(`QUOTENAME`)로
데이터베이스를 순회하므로 등록된 DB 수가 많으면 무거워질 수 있다(참고만, 이 문서의 실측 대상은 아님).

## 3. 폐쇄망 측정 방법

### 3.1 앱이 실행한 SQL을 v$sql/v$sqlarea에서 찾기

**중요한 전제**: 이 앱은 어디에서도 `DBMS_APPLICATION_INFO.SET_MODULE`/`SET_ACTION`이나 JDBC의
`v$session.program` 커넥션 속성을 설정하지 않는다(코드 전체 검색 결과 없음). 즉 `MODULE`/`ACTION` 기준으로는
구분할 수 없다. 대신 다음 조합으로 특정해라.

- **접속 계정**: `databases.json`/`dbconfig.db`에 등록된 이 DB의 모니터링 계정명(`PARSING_SCHEMA_NAME` 또는
  `v$session.username`). 운영 업무 계정과 겹치지 않는 전용 계정을 쓰는 것이 이 앱의 전제(코드 주석 "이 계정은
  모니터링 전용이라 다른 실사용자가 쓸 일이 없음")이므로, 이 계정 하나만으로도 상당히 좁혀진다.
- **접속 호스트**: `v$session.machine` = AIX 앱 서버 호스트명.
- **PROGRAM**: Oracle JDBC Thin 드라이버는 별도 설정이 없으면 보통 `JDBC Thin Client`로 남는다(드라이버
  버전에 따라 다를 수 있음 - 실측 필요).

```sql
-- 1) 이 앱이 지금 실행 중인 세션/SQL 확인
SELECT s.sid, s.serial#, s.sql_id, s.event, s.last_call_et, s.machine, s.program
FROM v$session s
WHERE s.username = '<모니터링 계정명>'
ORDER BY s.last_call_et DESC;

-- 2) 이 계정이 실행한 SQL의 누적 통계(가장 무거운 것부터) - PARSING_SCHEMA_NAME 기준
SELECT sql_id, parsing_schema_name, executions,
       ROUND(elapsed_time/1e6, 2)  AS elapsed_sec_total,
       ROUND(elapsed_time/DECODE(executions,0,1,executions)/1e6, 3) AS elapsed_sec_per_exec,
       ROUND(buffer_gets/DECODE(executions,0,1,executions), 0)      AS buffer_gets_per_exec,
       ROUND(disk_reads/DECODE(executions,0,1,executions), 0)       AS disk_reads_per_exec,
       rows_processed, last_active_time,
       SUBSTR(sql_text, 1, 200) AS sql_text
FROM v$sqlstats
WHERE parsing_schema_name = '<모니터링 계정명>'
ORDER BY elapsed_time DESC
FETCH FIRST 30 ROWS ONLY;   -- 11g면 FETCH FIRST 대신 WHERE ROWNUM <= 30로 감싸서 사용
```

### 3.2 대표 SQL 텍스트로 직접 찾기 (LIKE 패턴)

MODULE/ACTION이 없으므로, 2장 표의 "대상 뷰"에 적힌 핵심 테이블/뷰 이름으로 `v$sql`을 검색하는 편이 확실하다.
쿼리 전문은 이 문서의 대응 절(위 2.x)이 아니라 소스 파일에서 그대로 복사해 쓰는 것을 권한다(문자열이 정확히
일치해야 LIKE가 걸린다). 자주 찾을 대표 패턴:

```sql
-- 1번 우선순위: 성능 이력 조회(AWR 미프루닝 의심 쿼리)
SELECT sql_id, executions, elapsed_time, buffer_gets, last_active_time, SUBSTR(sql_text,1,4000) AS sql_text
FROM v$sqlstats
WHERE sql_text LIKE '%dba_hist_active_sess_history%'
  AND sql_text LIKE '%combined_ash%'
ORDER BY elapsed_time DESC;

-- 2번 우선순위: v$lock 스캔 계열(TM Lock Tree / active_alerts / failure_prob / Lock 실시간)
SELECT sql_id, executions, elapsed_time, buffer_gets, SUBSTR(sql_text,1,4000) AS sql_text
FROM v$sqlstats
WHERE sql_text LIKE '%FROM v$lock%' OR sql_text LIKE '%FROM V$LOCK%'
ORDER BY elapsed_time DESC;

-- 7번 우선순위: v$sqlstats 자체 델타 수집 쿼리(자기 자신을 찾는 메타 쿼리 - last_active_time 조건으로 식별)
SELECT sql_id, executions, elapsed_time, buffer_gets
FROM v$sqlstats
WHERE sql_text LIKE '%FROM v$sqlstats WHERE last_active_time%';
```

### 3.3 특정 SQL_ID의 실제 실행계획 (DBMS_XPLAN.DISPLAY_CURSOR)

```sql
-- sql_id를 위 3.1/3.2에서 찾은 뒤:
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('&sql_id', NULL, 'ALLSTATS LAST'));

-- 커서가 이미 라이브러리 캐시에서 밀려났다면(자주 있음) 이 앱의 "실행계획" 메뉴(2.8절
-- ExecutionPlanService.explainActual)로 같은 쿼리를 직접 실행해 즉시 통계를 뽑는 편이 더 확실하다.
```

### 3.4 dba_hist_active_sess_history 파티션 프루닝 여부 확인 (1번 우선순위 실측)

```sql
EXPLAIN PLAN FOR
SELECT session_id, session_serial#, sql_id
FROM dba_hist_active_sess_history
WHERE sample_time BETWEEN TO_DATE('2026-09-01 00:00','YYYY-MM-DD HH24:MI')

-- snap_id 프루닝이 안 걸리고 있다는 뜻 - 2.4절에서 지적한 문제가 실측으로 확인된다.
```

### 3.5 v$lock 스캔 소요 시간 직접 측정 (2번 우선순위 실측)

```sql
SET TIMING ON;
SELECT COUNT(*) FROM v$lock;                       -- 기본 스캔 비용
SELECT COUNT(*) FROM v$lock WHERE request > 0;      -- Lock 실시간/session_extra가 쓰는 조건
-- MonitorService.getTmLocks()와 동일한 self-join 재현(더 무거운 버전):
SELECT COUNT(*) FROM v$lock hl JOIN v$session hs ON hl.sid = hs.sid
LEFT JOIN v$lock wl ON hl.id1 = wl.id1 AND hl.id2 = wl.id2 AND wl.request > 0
WHERE hl.block = 1;
```

| `dbagent.sql-runner.read-only` | true | SQL 실행기 안전장치(성능과는 별개, 끄면 실수로 DML 실행 위험) |

폐쇄망에 없는 프로퍼티는 코드 기본값이 그대로 적용된다(`application.properties`는 skip-worktree라 새 키가 자동으로
반영되지 않는다는 메모리 기록 참고 - 새 키를 실제로 적용하려면 폐쇄망 파일에 직접 추가해야 한다).

## 4. 이 문서에서 실측하지 못하고 추정/코드 근거만으로 판단한 부분

- **로컬 Oracle XE(도커, 19c) 환경 특성상**, 이 문서의 "부하 등급"은 대부분 **폐쇄망의 실제 데이터량(세션 수,
  공유 풀 크기, 딕셔너리 객체 수, AWR 보관 기간)에 정비례**한다. 로컬 XE는 테이블 수·세션 수가 적어 위 쿼리들이
  대부분 순식간에 끝나므로, 로컬에서 "빨랐다"는 확인만으로 폐쇄망에서도 빠르다고 결론 내리면 안 된다.
- 2.4절 "성능 이력 조회"의 snap_id 미프루닝 문제는 **코드를 읽고 판단한 것**이며, 이 세션에서 실제 EXPLAIN PLAN으로
  파티션 프루닝 여부를 확인하지는 않았다(로컬 XE는 AWR 스냅샷/보관 기간이 짧아 이 문제를 실측으로 재현하기 어려움).
  3.4절 SQL로 폐쇄망에서 직접 확인해라.
- v$lock 스캔 "49초" 실측치는 **코드 주석에 남은 폐쇄망 실측 기록을 인용**한 것이며, 이 세션에서 직접 측정한 값이
  아니다. 폐쇄망 인스턴스별로 편차가 클 수 있으니 3.5절로 각 인스턴스마다 다시 재는 것을 권한다.
- `v$session.program`이 실제로 `JDBC Thin Client`로 남는지는 **드라이버 버전/설정에 따라 달라질 수 있어** 이
  세션에서 직접 확인하지 못했다 - 폐쇄망에서 3.1절 1번 쿼리로 먼저 확인해라.
- Current Session 화면의 정확한 폴링 주기가 `dbagent.ui.polling-interval-ms` 하나로 통일돼 있는지, 아니면 위젯별로
  다른 값(코드 주석 중 "5초 간격" 언급과 프로퍼티 기본값 2초가 다름)을 쓰는지는 `app.js`의 실제 바인딩까지는 이
  세션에서 전부 추적하지 못했다 - 프런트 실측(브라우저 네트워크 탭)으로 최종 확인해라.
- RAC 환경 특유의 `gv$`/인스턴스 간 조정 비용은 이 앱이 설계상 `gv$`를 쓰지 않도록(2026-09-06 결정) 최소화돼
  있지만, RAC의 GRD(Global Resource Directory) 부하 자체(다른 인스턴스가 보유한 락 정보를 얻어오는 비용)는 이
  문서의 SQL 텍스트만으로는 드러나지 않는다 - RAC 폐쇄망에서는 3.5절 v$lock 측정을 각 인스턴스에서 개별로 해라.
