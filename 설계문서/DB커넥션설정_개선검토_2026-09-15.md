# DB 커넥션 설정 개선 검토 (2026-09-15)

세션 중 대화로 진행한 검토 내용 정리. 코드 변경은 아직 없음 - 방향 확인 단계.

## 배경

- `databases.json`에 DB 인스턴스를 추가할 때마다 `tnsnames.ora`에도 alias를 등록해야 하는 번거로움이 있음.
- 과거 `databases.json`의 id/sid 중복으로 엉뚱한 DB에 붙는 사고가 두 번 있었음("포탈 #1/#2" id 중복, "기타" 그룹 id 재사용 - `dbagent-java-overview` 메모리 참고). 지금도 "포탈 #1"/"포탈 #2"가 같은 sid(`ORCL5`)를 쓰고 있어 의도된 것인지 확인 필요.
- `oracle.env`가 정확히 어떤 역할을 하는지, 없앨 수 있는지 궁금해서 코드를 같이 확인함.

## 현재 코드 구조 (확인 완료)

### DSN 생성 - `OracleConnectionPoolManager.buildDsn()`

```java
private String buildDsn(TargetDbConfig target) {
    String host = target.host();
    if (host != null && !host.isBlank()) {
        return host + ":" + target.port() + ":" + target.sid();   // 직접 접속, tnsnames.ora 불필요
    }
    return target.sid();   // host 비어있으면 sid를 TNS alias로 취급 -> tnsnames.ora 필요
}
```

**IP 직접 접속 방식은 이미 코드로 지원되고 있음.** 지금 `databases.json`의 모든 인스턴스가 `host`를 빈 문자열로 둔 채 `sid`를 TNS alias로만 쓰고 있어서 tnsnames.ora 등록이 필요한 것뿐 - `host`(IP)와 진짜 SID만 채우면 코드 변경 없이 바로 직접 접속으로 전환됨.

**주의**: 지금 코드는 `host:port:sid`(콜론) 형식만 만듦. 요즘 오라클은 service_name 기반(EZ Connect: `host:port/service_name`, 슬래시)을 쓰는 경우가 많아서, 대상 DB가 service_name 방식이면 `buildDsn()`에 분기 추가가 필요할 수 있음 - **실제 전환 전에 대상 DB들이 SID/service_name 중 어느 쪽인지 확인 필요**.

### TNS_ADMIN 설정 - `TnsAdminInitializer`

```java
@Value("${dbagent.oracle.tns-admin:}")
private String tnsAdmin;
...
void init() {
    String resolved = (tnsAdmin != null && !tnsAdmin.isBlank()) ? tnsAdmin : deriveFromOracleHome();
    if (resolved != null && !resolved.isBlank()) {
        System.setProperty("oracle.net.tns_admin", resolved);
    }
}
```

`application.properties`의 `dbagent.oracle.tns-admin`이 이미 1급 설정값이며, 이 값이 채워져 있으면 `oracle.env`의 `ORACLE_HOME` 줄은 읽지도 않음. 즉 **TNS_ADMIN은 이미 `application.properties`에 직접 설정 가능** (현재는 의도적으로 비워두고 `oracle.env`의 `ORACLE_HOME`에서 유도하도록 되어 있음 - `application.properties` 주석 참고).

### `oracle.env`의 실제 역할 (ORACLE_HOME만 쓰는 게 아님)

`oracle.env`는 코드에서 **두 군데서 서로 다른 용도로** 읽힘:

1. `TnsAdminInitializer` - `ORACLE_HOME` 한 줄만 읽어서 tns-admin 미설정 시 `{ORACLE_HOME}/network/admin`을 유도 (위 항목)
2. `DatabaseConfigService.loadOracleEnvFallback()` - `USER`/`PASSWORD`/`HOST`/`PORT`/`SID`를 읽어서 **"기본 DB"**(`resolve()`가 `db_id`가 빈 문자열일 때 돌려주는 `"Default (oracle.env)"` 인스턴스)를 만듦. 로그인 직후처럼 아직 특정 DB를 고르기 전에 나가는 요청들이 이 fallback을 탐.

→ IP 전환 + tns-admin 직접 설정을 해도 `oracle.env`의 `USER/PASSWORD/HOST/PORT/SID` 줄(기본 DB fallback)은 여전히 쓰이므로, **파일 자체를 완전히 없애려면 이 fallback 로직도 같이 손봐야 함**.

## 제안 (우선순위 순)

1. **id/sid 중복 검증** - 기동 시(`DatabaseConfigService.init()`) `databases.json` 전체를 훑어 id/sid 중복을 로그로 경고. 적은 코드로 재발 방지 효과가 큼. 처음엔 "기동 실패"가 아니라 "경고 로그"로 시작 (기존 중복이 있으면 앱이 안 뜨는 걸 방지).
2. **IP 직접 접속 전환** - `databases.json`의 `host`(+ 필요시 SID/service_name 포맷) 필드를 채워 tnsnames.ora 의존 제거. 코드 변경 없이 데이터만 채우면 됨 (SID vs service_name 포맷 확인 후 필요시 `buildDsn()`에 분기 추가).
3. **TNS_ADMIN을 `application.properties`에 직접 설정** - IP 전환이 끝나면 tns-admin/tnsnames.ora 자체가 불필요해짐. 과도기엔 명시적으로 설정.
4. **`oracle.env` 의존 축소** - 위 1~3이 끝나면 `oracle.env`의 `ORACLE_HOME` 줄은 무의미해짐. `USER/PASSWORD/HOST/PORT/SID`(기본 DB fallback) 줄까지 없애려면 `databases.json`에 `"default": true` 같은 플래그를 둔 인스턴스를 기본값으로 쓰도록 `DatabaseConfigService`를 리팩터링해야 함 - 별도 작업.
5. (선택) 비밀번호가 Base64 인코딩일 뿐 실제 암호화가 아님(`DatabaseConfigService.resolvePassword`/`encodePassword` 주석에 명시) - 별도 주제로 논의 가능.
