# 최소(minimal) Agent 적용 검토 (2026-09-15)

세션 중 대화로 진행한 설계 검토. 코드 변경은 아직 없음 - 방향/설계 확인 단계.

## 배경

DB 모니터링 도구의 "Agent 방식"(대상 서버에 수집 프로그램 설치) vs 지금 DBAgent-Java의 "Agentless 방식"(중앙 서버가 JDBC로 직접 폴링, `MonitorController.fleetStatus()` 등)을 비교하는 대화에서 출발. 전면적인 agent 아키텍처 전환은 배보다 배꼽이 커서, **지금 구조는 그대로 두고 JDBC/V$ 뷰로 구조적으로 못 보는 항목만 agent로 보완**하는 쪽으로 범위를 좁힘(사용자 제안, 2026-09-15).

## 적용 범위 - Agent로만 수집 가능한 항목 정리 (2026-09-15 업데이트)

JDBC/SQL(V$ 뷰 등)은 "DB 프로세스가 살아서 응답할 때, DB 인스턴스 내부에서 보이는 것"만 볼 수 있다는 구조적 한계가 있음. 아래는 그 한계를 벗어나 **OS 파일시스템/프로세스에 직접 접근해야만 얻을 수 있는 항목**들.

### 1) OS 호스트 자원
- CPU/메모리/스왑 사용률, load average
- 디스크 free space(데이터파일이 앉은 볼륨 포함 - 테이블스페이스 사용률은 SQL로도 보이지만 "볼륨 자체가 꽉 찼는지"는 OS만 앎), 디스크 I/O 지연(iostat류)
- 네트워크 I/O, 소켓/연결 상태
- Oracle은 `V$OSSTAT`으로 일부 흉내 내지만 MySQL/MariaDB/MSSQL/PostgreSQL/CUBRID는 이런 창구 자체가 없음

### 2) 로그 파일 기반 (OS 파일시스템에만 존재)
- **alert log(`alert_SID.log`) 실시간 tail + 모니터링 화면 노출**: ORA- 에러 발생 "순간"을 SQL 폴링으로는 못 잡음(사후에 `v$diag_alert_ext`로 찾을 순 있지만 실시간성이 없고, 이마저 Oracle 전용 - 타 DB엔 없음). agent가 파일을 tail하면 실시간 push 가능하고, 현재 대시보드 화면에 "Alert Log" 탭/패널로 최근 라인을 그대로 보여줄 수 있음(사용자 요청, 2026-09-15) - RDB 대시보드의 기존 세션/락 화면과 같은 자리에 패널 하나 추가하는 정도로 충분.
- listener log (접속 시도/거부 이력 - 방화벽/네트워크 문제 진단에 필요)
- OS 레벨 에러 로그(`dmesg`, `/var/log/messages` 등) - **OOM killer가 DB 프로세스를 강제 종료한 경우**, JDBC 쪽에서는 그냥 "커넥션이 끊겼다"로만 보이고 원인을 전혀 알 수 없음. 이게 OS 로그에만 남음.

### 3) SQL 트레이스/tkprof - 실행계획보다 더 깊은 실측 통계
- 현재 "AI Current SQL 분석"(1차 성능점검)은 `V$SQL_PLAN`/실측 통계 기반 실행계획까지만 보여줌. **tkprof**는 `SQL_TRACE`/10046 이벤트로 떨어진 raw trace 파일을 파싱해 **호출별(Parse/Execute/Fetch) CPU/elapsed/physical reads/logical reads/wait event 분해**까지 보여주는, 실행계획보다 한 단계 더 깊은 진단 도구.
- 구조적으로 agent가 필요한 이유: trace 활성화 자체는 `DBMS_MONITOR.SESSION_TRACE_ENABLE` 등으로 JDBC(SQL)로도 가능하지만, **① 만들어진 trace 파일은 DB 서버의 OS 파일시스템(`user_dump_dest`/`diagnostic_dest/.../trace`)에만 존재**하고, **② `tkprof` 자체가 OS 커맨드라인 유틸리티**라 SQL로는 절대 실행/조회 불가능. agent가 해당 디렉터리에서 최신 trace를 찾아 `tkprof` 실행 후 결과 텍스트를 push하면, "AI SQL Tunner" 쪽에 "tkprof 결과" 탭을 하나 추가해서 1차 성능점검보다 더 깊은 분석이 필요할 때 볼 수 있게 할 수 있음(사용자 요청, 2026-09-15) - 이러면 "1차 성능점검(V$SQL_PLAN) → 2차 성능분석(AI) → (필요시) tkprof 상세"까지 단계가 자연스럽게 이어짐.

### 4) 장애 원인 진단
- **DB가 완전히 죽었을 때의 원인 구분**: 지금은 JDBC 커넥션 실패 시 "타임아웃/거부"만 보이고 왜 죽었는지 모름. agent는 호스트가 살아있는 한 "DB만 죽었다 + 원인(archiver stuck, 디스크 풀, OOM 등)"까지 구분 가능.
- ADR(Automatic Diagnostic Repository)의 incident/core dump 파일 존재 여부 - 심각한 장애의 증거가 OS 파일로만 남음

**기존 JDBC 흐름(세션/락/테이블스페이스 조회, fleet status, AI Current SQL 분석 등)은 전혀 안 건드림** - 위 네 가지는 전부 화면에 새 패널/탭을 추가하는 형태의 순수 추가(additive)만 함.

### 5) RAC 영역 - Clusterware 레벨만 (GV$ 기반 수집은 채택 안 함)

Oracle RAC는 `GV$` 뷰(Global V$)로 클러스터 전체 데이터를 인스턴스 하나 접속만으로 볼 수 있긴 하지만, **GV$ 조회는 속도 문제로 이번 범위에서 제외**(사용자 결정, 2026-09-15 - GV$가 인스턴스 간 내부 RPC로 데이터를 모으는 구조라 노드 수·부하에 따라 느려질 수 있음). 대신 **Clusterware(OS/클러스터웨어) 레벨만 agent로 수집**:

- **CRS/Grid Infrastructure 리소스 상태** - `crsctl status resource -t`, `srvctl status database` 같은 OS 명령으로만 확인 가능한 VIP/SCAN 리스너/ASM 인스턴스 기동 상태
- **노드 eviction(강제 재부팅) 이력** - 하트비트 실패로 CSS가 노드를 쫓아낸 순간은 그 노드가 죽어버려 SQL로는 못 잡음, 클러스터웨어 로그(`ocssd.log`, `crsd.log`)에서만 확인 - "DB 다운 원인 진단"(4번 항목)의 RAC 버전
- **Private interconnect(Cache Fusion 전용망) 상태** - NIC 에러/패킷 드랍 등 OS(`netstat`/`ifconfig`) 레벨 원인
- **OCR/Voting Disk 건강 상태** - `ocrcheck`, `crsctl query css votedisk`

**구조적 차이**: RAC는 노드가 여러 대이므로 **agent를 노드당 한 개씩 배포**해야 함(지금까지의 "DB 1대당 agent 1개" 전제가 RAC에서는 "DB 1개, 노드 N개, agent N개"로 바뀜). 저장 스키마의 `metric_type`/구분 키에 노드 식별자(instance_name/node_name)를 추가해서 노드별로 구분 저장해야 함.

## 아키텍처 - Push 방식, 새 엔드포인트 하나

- `POST /api/agent/report` 같은 새 엔드포인트를 추가하고, 대상 DB 옆에 떠 있는 최소한의 스크립트(파이썬/쉘 한 개, OS metrics는 cron 주기 실행, alert log는 `tail -f` 방식)가 주기적으로 수집한 값을 이 엔드포인트로 push.
- 이 앱이 이미 sqlrestapi(폐쇄망 GPU 서버)와 REST로 통신하는 패턴을 갖고 있어서, "별도 프로세스가 REST로 데이터를 주고받는다"는 아키텍처 자체는 새롭지 않음 - 방향만 반대(이번엔 외부에서 이 앱으로 push).
- 망 분리 등으로 중앙 서버가 직접 못 붙는 DB에 한해서만 선택적으로 적용 가능(전체 DB에 강제할 필요 없음).

## 저장 구조 - 메모리 캐시만으론 부족, SQLite 필요

처음엔 "최신 값만 보여주면 되면 메모리 캐시로 충분"하다고 봤으나(`MonitorController`의 `fleetStatusInFlight` 같은 `ConcurrentHashMap` 패턴 재사용 가능), **"과거 특정 시점 데이터 조회"가 요구사항으로 확정**되면서 영속 저장이 필요해짐(사용자 확인, 2026-09-15).

이 앱은 이미 `users.db`(SQLite)를 인증/세션 저장에 쓰고 있어서, 새 RDBMS를 얹기보다 **같은 SQLite 패턴을 그대로 재사용**하는 게 가장 적은 변화:

- 테이블 초안: `(db_id, metric_type, collected_at, value/json)` - `collected_at`에 인덱스를 걸어두면 "특정 시점 조회"가 `WHERE collected_at BETWEEN ...`로 바로 됨
- `metric_type`으로 OS자원/디스크/alert_log_line 등을 한 테이블에서 구분하거나, 종류별로 테이블을 나눠도 됨(alert log는 텍스트 라인이라 스키마가 다르므로 별도 테이블이 더 자연스러울 수 있음 - 구현 시 결정)

## 보존(retention) 정책 - 설정값으로 뺄 것 (15일/30일 선택 가능하게)

이 앱에 이미 정확히 같은 패턴의 선례가 있음 - `AuthService.cleanupExpiredSessions()`:

```java
@Scheduled(cron = "0 0 3 * * *")   // 매일 새벽 3시
void cleanupExpiredSessions() { ... }
```

기준 기간은 `application.properties`의 `dbagent.auth.session-ttl-days=30`처럼 설정값화되어 있음. agent 데이터도 동일하게:

- 새 설정값 `dbagent.agent.retention-days` 추가 (기본값은 추후 결정 - 15일 또는 30일 중 운영하면서 조정 가능하게, 하드코딩하지 않음)
- 같은 새벽 3시 스케줄(또는 별도 `@Scheduled`)에 `DELETE WHERE collected_at < now - retention-days` 정리 작업 추가

**사용자 요청(2026-09-15)**: 보존 기간은 15일/30일 둘 다 상황에 맞게 쓸 수 있도록 **설정값으로 제공**할 것 - 코드에 고정하지 말고 `application.properties` 한 줄 수정으로 바꿀 수 있게.
