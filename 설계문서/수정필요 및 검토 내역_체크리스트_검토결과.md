## 1번째 (Current Session 매뉴) — 항목이 가장 많고 우선순위 판단 필요

### 1-1. CPU 개수 쿼리 변경 — **확정**
- 코드 확인 결과 이미 `MonitorService.java`에서 `v$osstat.NUM_CPUS`를 사용 중(라인 ~322, ~1019, ~1102, ~1794). 체크리스트가 요청한 `NUM_CPU_CORES`가 아님.
- 2026-09-22 design-advisor 검토에서 "화면마다 코어 수가 갈리는 문제"를 막기 위해 기존 v2 대시보드와 값을 통일한 것으로 보이나, stat_name 선택 자체가 잘못됨.
- **오케스트레이터가 폐쇄망 실DB에서 실측 확인(2026-09-24): `NUM_CPU_CORES` 값이 실제 서버 코어 수와 일치.**
- **결론: `v$osstat.NUM_CPU_CORES`로 통일. 4곳(라인 ~322, ~1019, ~1102, ~1794) 전부 같이 변경해야 재발 방지.** 한 곳만 바꾸면 화면마다 코어 수가 다시 갈리는 문제가 재발함.
- **정정 (2026-09-25, 구현 시 확인)**: 실제로는 5곳(샘플러 포함)이고, 그중 3곳은 코어 수가 아니라 **CPU 사용률(%)의 분모**였다. 로컬 실측 NUM_CPUS=32 / NUM_CPU_CORES=16(SMT)이라 분모까지 코어로 바꾸면 CPU%가 2~8배로 부풀어 100%를 넘는다. 오케스트레이터 결정으로 **코어 기준선 2곳만 `NUM_CPU_CORES`(공통 헬퍼 `CpuCores`), CPU% 분모는 `NUM_CPUS` 유지**로 완료.

### 1-2. 폐쇄망 환경 그래프 로딩 성능 문제
- 재현 조건(인터넷망 정상, 폐쇄망만 느림)이 핵심 단서. 원인이 네트워크 지연인지 초기 쿼리(ASH 풀스캔) 자체가 무거운지 구분하는 조사가 선행되어야 함.
- "그래프 틀이라도 먼저 보이게" 요구는 로딩 스켈레톤/스피너 UI 추가로 비교적 간단히 개선 가능.
- 1-5와 함께 "그래프 렌더링 안정성" 묶음으로 처리 권장.

### 1-3. 우측 그래프(Top SQL Activity Timeline) 드래그 기능 개선
- 색상 단위 정교한 드래그 vs 현재 세로 구간 단위 드래그 — 의도된 동작인지 원 개발 시점 확인 필요.
- 좌측 그래프(Active Session Wait Class) 드래그 기능은 신규 구현 필요.

### 1-4. Active Session 리스트 7개 이상 시 스크롤바
- 난이도 낮음, 독립 작업 가능.

### 1-5. DB 전환/RDB·FO 왕복 후 그래프 갱신 안 됨(검은 화면) — **버그**
- 폴링 타이머 clearInterval 누락 또는 이전 DB 응답이 늦게 도착해 새 DB 화면을 덮어쓰는 레이스 컨디션 의심.
- 1-2와 함께 우선 처리 권장.

### 1-6. 우측 그래프도 좌측처럼 색상 계열 클릭 시 필터링
- 난이도 중간, 좌측 그래프 기능을 우측에 이식하는 형태.

### 1-7. Duration Time(sec) 필드 클릭 시 오름/내림차순 정렬
- 첫번째 대시보드 + Current Session 매뉴 양쪽 적용.

### 1-8. 탭 메뉴 구조 변경 (Remote 탭 신규 추가)
- 첫번째 대시보드: Active 세션/Top 이벤트 → Active Session, Active Transaction, Parallel Session, Remote, 2pc Pending Transaction, Top Events
- Current Session 매뉴: 기존 탭 구성에 Remote 탭 신규 추가
- 메인 대시보드/Current Session 양쪽 다 손대야 해서 범위가 상대적으로 큼.

### 1-9. 리프레쉬 주기 3초 디폴트 (현재 5초) — **확인 필요**
- "현재 5초"의 실제 코드 위치를 특정하지 못함. 확인된 관련 프로퍼티: `dbagent.ui.polling-interval-ms=2000`(대시보드), `ASH_ACTIVITY_POLL_MS=30000`(차트, app.js 하드코딩).
- Current Session 전용 타이머가 별도로 있는지 추가 확인 필요.
- 질문하신 "리프레쉬 주기 설정 시 좌/우 그래프+Active Session 리스트가 함께 적용되는지"는, 현재 서로 다른 타이머(대시보드 폴링 vs ASH_ACTIVITY_POLL_MS)로 분리되어 있어 **"아니오"에 가까움** — 통일할지 별도 유지할지 결정 필요.
- 리스트가 그래프보다 먼저 나타나는 현상도 이 폴링 분리 구조 때문으로 추정.

## 2번째 (성능이력 그래프 개편) — **설계 완료 + 방향 확정, 메뉴명 "성능 분석"으로 변경**

**메뉴명 변경 확정(2026-09-24)**: "성능 이력 조회" → **"성능 분석"**. 산점도 기반 "이력 조회"에서 wait class/event 드릴다운 기반 "분석" 화면으로 성격이 바뀐 것을 반영.

design-advisor 에이전트 상세 설계 완료(2026-09-24), 이후 오케스트레이터가 최종 방향을 확정. 전체 내용은 `성능이력조회_개편_검토_2026-09-24.md` 참고.

**확정된 최종 방향**: 산점도(개별 느린 쿼리 나열) 방식은 업무 관련성과 무관하게 단순히 느린 쿼리만 보여줘 실질적 성능 분석에 부적합하다는 판단하에 폐기. 대신 **Current Session 매뉴의 Active Session Wait Class 그래프를 과거 임의 구간에 대해 보여주는 방식**으로 전환, 3단 드릴다운 구조로 확정:
- **상단**: 선택한 과거 구간의 wait class 히스토리 막대 그래프(기존 Active Session Wait Class와 동일 카테고리/색상 체계 — cpu/latch/user_io/tx_lock/system_io/tm_lock/other), 시간축 드래그로 구간 선택
- **하단**: (2026-09-24 변경) "느린 세션 목록" 대신, 상단과 **같은 선택 구간** 기준 **event별 막대 그래프**(wait_category보다 한 단계 세분화된 원본 event명 단위 — 예: "db file sequential read"). Oracle AWR "Top Timed Events"와 같은 패턴으로, 업무 관련성과 무관하게 느린 세션만 나열되던 기존 문제를 구조적으로 해결.
- **드릴다운**: 하단 event 막대 클릭 시 해당 event의 세션 목록을 팝업으로 표시.
- **필드 통일**: 이 세션 목록 팝업에 `getSessions()`(Dashboard+Current Session 공통) 필드셋을 적용하되, `status`/`session_wait_pct`/`has_transaction` 3개는 과거 시점 조회에 불필요하다고 확정(제외).
- **팝업 통일**: 이 세션 목록 팝업을 포함해 **환경설정 팝업을 제외한 모든 팝업**을 4번째 그룹 1~3번 스펙(초기 크기 80%, 세로→가로 통일, 세션 상세정보 표 재구성)으로 통일 — 즉 이 작업이 팝업 통일의 첫 적용 사례가 됨.

**기술적으로 확인된 사항**:
- 데이터 소스는 `getAshActivity()`(현재 실시간 "최근 N분"만 지원)를 시작/종료 시각 파라미터화 + AWR(`dba_hist_active_sess_history`) 폴백으로 확장해야 함. 이때도 원래 설계의 원인 C(ASH 롤오버/AWR 보존기간·Diagnostic Pack 라이선스)가 그대로 적용되므로 폐쇄망 실측(8절 1번)이 여전히 필요.
- 기존 산점도 대체안 중 "옵션 2(시간 버킷 누적 막대)"를 채택한 것과 동일. 다만 중단의 "개선 산점도" 레이어는 없이 2층(그래프+목록) 구조로 단순화됨.
- 항목 2(SQL 텍스트 검색)/항목 3(쿼리 타입 색상)은 폐기가 아니라 메인 그래프가 아닌 "하단 목록/세션 상세팝업의 부속 기능"으로 역할 재조정됨.
- 1-3(체크리스트 1번째 그룹, 좌측 그래프 드래그 미구현) 항목과 시간축 드래그 구현을 같이 처리하면 코드 재사용 가능.

재정리된 착수 순서: `설계문서/성능이력조회_개편_검토_2026-09-24.md` 9.2절 참고 (①getAshActivity 확장 ②wait class 히스토리 그래프(상단) ③시간축 드래그 ④event별 막대 그래프(하단) ⑤event 막대 클릭 시 세션 목록 팝업을 4번째그룹 스펙으로 신규 제작 ⑥필요시 자체 적재).

**세션 조회 목록 필드 통일(2026-09-24 오케스트레이터 지적+확정, 9.3절)**: Dashboard와 Current Session의 Active Session 목록은 `getSessions()`를 공유해 필드가 동일(18개)하지만, 성능 이력 조회(`getHistorySessions()`, 11개)는 필드 구성이 다름을 확인. Lock Holder/Waiter Tree(트리 구조라 목록형과 다름)를 제외한 모든 세션 조회 목록의 필드를 일관되게 통일하기로 확정 — event 막대 클릭 시 뜨는 세션 목록 팝업을 새로 만들 때 반영. **`status`/`session_wait_pct`/`has_transaction` 3개는 불필요하다고 확정되어 제외**, 나머지 필드로 통일.

## 6번째 (AI 챗봇 system prompt 변경) — **분류 기준 확정**

- 오류 코드 질문 → Vector DB 근거 답변 유지, 오류 외 질문 → 모델 자체 지식 허용으로 변경 요청.
- **분류 기준 확정(2026-09-24, 오케스트레이터): 질문에 `ORA-nnnnn` 형식의 오류 코드가 포함되면 오류 관련으로 판단.** 정규식 패턴 매칭(예: `ORA-\d{4,5}`)으로 system prompt 분기 또는 전처리 단계에서 판별 가능.
- **환각 리스크 허용 범위 확정(2026-09-24, 오케스트레이터): "중간 리스크까지 허용."**
  - 허용(모델 자체 지식으로 답변 OK): 일반 개념 설명(인덱스, REDO 로그 등), 버전/환경에 따라 달라질 수 있는 설명(파티션 재구성 지원 여부, 쿼리 최적화 방향 제안 등).
  - 불허(Vector DB 근거 없이는 답변 금지 또는 출처 불명확 명시 필요): 그대로 실행하면 위험한 명령/SQL 생성(테이블스페이스 축소, 세션 강제 종료 등), 실존 여부를 확인할 수 없는 버그 번호·패치 번호·MOS 노트 번호 인용.
  - system prompt 설계 시 이 경계를 명시적으로 반영해야 함(예: "실행 가능한 명령이나 특정 문서/버그 번호는 확실하지 않으면 생성하지 말고 모른다고 답하라" 지시 추가).
- **답변 허용 범위 확정(2026-09-24, 오케스트레이터): "오류 관련 질문 외"는 DB/오라클 범위로 한정하지 않고 DB와 무관한 주제도 포함.** 즉 오류코드가 없는 질문이면 DB 여부와 상관없이 모델 자체 지식으로 답변(중간 리스크까지) 허용.
